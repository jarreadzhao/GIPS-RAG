## 第 2 章 通用规则（11 份契约共同适用）

### 2.1 字段与类型

**判定问句**：两侧能否只靠这一节写出同样的校验代码？

公共类型约定如下，各契约不得自行另立：

| 类型 | 定义 | 空值语义 | 校验方 |
|---|---|---|---|
| `request_id` | 26 位 ULID，全局唯一 | 不允许为空 | 网关生成，全链透传 |
| `task_id` / `finding_id` | 前缀 + 26 位 ULID（`tsk_` / `fnd_`） | 不允许为空 | 创建方生成 |
| `chunk_id` | 32 位十六进制 | 不允许为空 | 离线构建生成 |
| `index_version` | `YYYYMMDD.HHmm` + 两位序号，如 `20261107.1130.01` | 不允许为空 | 离线构建生成 |
| `profile_version` | 整数，单调递增 | 不允许为空 | profile 服务生成 |
| `acl_scope` | 字符串数组，元素形如 `dept:FUND` 或 `clr:internal` | **空数组与缺失不同义**：缺失即拒绝，空数组合法但只匹配公开件 | 网关注入 |
| `span_text` | UTF-8 原文片段，不含首尾空白 | 不允许为空 | 回验器校验 |
| `span_hash` | `sha256:<64 位小写十六进制>` | 不允许为空 | 回验器校验 |
| `char_start` / `char_end` | 32 位整数，左闭右开，按 Unicode 码点计 | 不允许为空 | 回验器校验 |
| `page_no` | 整数，从 1 起 | 不允许为空 | 解析器写入 |
| `calc_id` | `calc_` + 26 位 ULID | 不允许为空 | 计算器生成 |
| `verdict` | 枚举 `SUFFICIENT` / `PARTIAL` / `GAP` / `INSUFFICIENT_EVIDENCE` | 不允许为空 | 台账校验 |
| `confidence` | 0 到 1 的定点小数，保留三位 | 允许为空，空表示未给出 | 不参与判定 |
| 时间 | RFC 3339，UTC，毫秒精度 | 不允许为空 | 各服务 |

三条禁止：不得用 `null` 表达「未知」与「本条不涉及」两种语义（必须用枚举区分）；不得用浮点数表示金额与比率（用字符串定点数）；不得在跨服务字段里放自由文本的错误描述（错误码与描述分离）。

### 2.2 成功与失败语义

**统一错误结构**

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | 枚举，见下表 | 机器判定唯一依据 |
| `message` | 字符串 ≤ 200 字 | 面向人，不得含内部路径与堆栈 |
| `retryable` | 布尔 | 由提供方判定，调用方不得自行推断 |
| `request_id` | ULID | 用于对账 |
| `details` | 对象，可空 | 仅放字段级校验信息 |

**错误码表（全局唯一，不得各契约自行扩展同义码）**

| code | HTTP | 触发条件 | retryable | 归属 |
|---|---|---|---|---|
| `ACL_SCOPE_MISSING` | 400 | 请求未携带 `acl_scope` | 否 | 调用方 |
| `ACL_DENIED` | 403 | 候选集为空且确有越权尝试 | 否 | 调用方 |
| `PROFILE_MISSING` | 400 | formal 任务缺 firm profile | 否 | 调用方 |
| `SUPPLY_NOT_ALLOWED` | 422 | `formal` + `managed` 组合 | 否 | 调用方配置 |
| `INDEX_NOT_ACTIVE` | 409 | 请求的 `index_version` 未处于 active | 是（切版本后） | 提供方状态 |
| `ANCHOR_INVALID` | 422 | 锚点字段缺失或条款不存在 | 否 | 生成方 |
| `SPAN_MISMATCH` | 422 | 字节级比对失败 | 是（重抽一次） | 生成方 |
| `CALC_NOT_ALLOWED` | 422 | `calc_id` 不存在或引擎版本不在清单 | 否 | 生成方 |
| `SQL_GUARD_REJECTED` | 400 | SQL 通道命中非白名单表或超行数 | 否 | 调用方 |
| `ROW_VERSION_CONFLICT` | 409 | 乐观锁版本不匹配 | 是（刷新后） | 调用方 |
| `IDEMPOTENCY_CONFLICT` | 409 | 同一幂等键不同载荷 | 否 | 调用方 |
| `DOC_HASH_MISMATCH` | 409 | 原件哈希与登记不一致 | 否 | 提供方数据 |
| `UPSTREAM_TIMEOUT` | 504 | 下游超时 | 视契约 | 提供方 |
| `UPSTREAM_RATE_LIMITED` | 429 | 供应商限流 | 是（退避） | 提供方 |
| `CACHE_KEY_INCOMPLETE` | 500 | 缓存 key 缺分量 | 否 | 提供方实现 |

**超时与重试归属（最容易扯皮的一节）**

| 场景 | 超时 | 谁重试 | 计费与副作用 |
|---|---|---|---|
| 检索单通道 | 800ms | 编排器可重试 1 次 | 幂等，无副作用 |
| 结构化查询 | 5s | 不重试 | 只读 |
| 重排 | 1s | 不重试，降级为 RRF 原序并标 `rerank_skipped=true` | 无 |
| 生成单步 | 60s | **不重试** | 重试会产生两份 token 计费与两条链，由用户手动重试 |
| 回验 | 2s | 不重试 | 超时按失败处理，整链作废 |
| 缓存读 | 50ms | 不重试，视为未命中 | 无 |
| 台账写入 | 3s | 用同一幂等键重试，最多 3 次 | 幂等键重复写入返回原结果 |

**成功判定**：只有 `2xx` 且业务体 `status` 为终态才算成功。`200` 携带 `RETRIEVAL_EMPTY` 属业务态而非错误，调用方不得据此重试。

### 2.3 身份与数据规则

| 项 | 规则 |
|---|---|
| 服务身份 | 服务间调用使用 mTLS + 服务令牌，令牌含 `service_id` 与允许调用的契约列表 |
| 用户身份 | 只在网关解析；下游服务接收 `actor_id` 与 `acl_scope`，不接收原始 JWT |
| ACL 注入 | 由网关从令牌计算并注入，下游不得接受客户端传入的 `acl_scope` |
| ACL 缺失 | 直接拒绝，不得「无过滤即查全库」 |
| 敏感字段 | `firm_profiles` 明文字段、`calc_results.value`、客户名映射不得出现在任何跨服务响应中 |
| 台账数据 | C 类只允许台账服务与计算器访问；检索、生成、缓存三条路径无账号权限 |
| 日志 | 请求体默认不落日志；需排查时落脱敏副本，保留 7 天 |
| 出域 | 所有携带 `corpus_type=B_internal` 的载荷必须带 `egress_class=approved`，缺标记拒绝 |

**这条是硬边界**：`acl_scope` 与 `egress_class` 都不是「建议字段」，缺失时提供方必须拒绝，不能补默认值。补默认值等于把越权变成默认行为。

### 2.4 状态与并发

**幂等键**

| 操作 | 幂等键 | 重复请求的行为 |
|---|---|---|
| 创建审查任务 | 客户端生成 `Idempotency-Key`，24 小时内有效 | 返回首次结果，不新建任务 |
| 上传文档 | `sha256(文件字节)` | 返回已存在的 `doc_id`，不重复入库 |
| 签署 finding | `finding_id + signer_id + row_version` | 返回当前签署状态；版本不同则 409 |
| 索引构建 | `doc_id + version_no + config_hash` | 返回已有构建记录 |

幂等键相同但载荷哈希不同 → `IDEMPOTENCY_CONFLICT`，不得「以后到的为准」。

**状态机**

索引构建（CT-4）：

| 当前 | 允许迁移 | 触发 | 禁止 |
|---|---|---|---|
| `pending` | `embedding`、`failed` | 质量闸门通过 / 解析失败 | 直接到 `active` |
| `embedding` | `indexed`、`failed` | 写入完成且计数一致 / 超时 | 跳过计数校验 |
| `indexed` | `active`、`failed` | 抽样回查通过 / 回查失败 | 未回查即 active |
| `active` | `superseded`、`rolled_back` | 新版本发布 / 评测退化 | 原地修改 |
| `failed` | `pending` | 清理后重试 | 直接 active |

审查任务（CT-2、CT-8）：

| 当前 | 允许迁移 | 说明 |
|---|---|---|
| `created` | `running`、`cancelled` | 校验通过才 running |
| `running` | `succeeded`、`failed`、`pending_retry` | 回验失败进 `failed`，不降级 |
| `pending_retry` | `running`、`cancelled` | 仅上游超时可进 |
| `succeeded` | 终态 | finding 待签署 |

finding 状态：`draft` → `pending_signoff` → `signed` → `finalized`；`signed` 可进 `disputed` 并生成新记录，旧记录 `superseded`。

**并发规则**

1. 签署用乐观锁 `row_version`，冲突返回 409 并提示刷新，**不得静默覆盖**。
2. 同一 `task_id` 的同时写入由台账服务串行化（单写队列），后到者排队而非失败。
3. 索引切换是单条 `UPDATE documents SET active_version = ?`，以数据库为准；Milvus 侧只做计数校验，不承担一致性判定。
4. 缓存写入与索引切换无事务关系，靠 `index_version` 天然隔离，不要求强一致。

### 2.5 兼容与版本

| 项 | 规则 |
|---|---|
| 契约版本 | 每份契约独立版本号，写在文首；不兼容变更升主版本 |
| 新增字段 | 必须可选且有明确默认值；客户端须容忍未知字段（不得因多字段报错） |
| 新增枚举值 | 视为兼容变更，但客户端遇未知值须走「无法判定」分支，不得当默认值处理 |
| 删除字段 | 先标 deprecated，保留两个里程碑，且期间双写；之后才可删 |
| 语义变更 | 同名字段语义变化视为不兼容，必须换名，不得原地改 |
| 错误码 | 只增不改；废弃码保留至少两个里程碑并继续返回 |
| 契约变更流程 | 走 CHG 变更单，四件套同步；接口文档与验收标准须在同一次提交内更新 |

**特别约定**：`verdict` 枚举不得新增第五态。若业务确需新态，必须走主版本升级并同步改判定链与统计口径——四态是台账统计与 GAP recall 的计算基础，静默扩展会让历史指标不可比。

### 2.6 责任划分

| 责任 | 归属 | 判据 |
|---|---|---|
| ACL 表达式正确 | 网关（生成）与检索（执行）共同承担 | 越权返回内容 → 检索方负责；表达式本身错 → 网关负责 |
| 检索为空是否属失败 | 编排器 | 空集必须作业务态返回，不得抛 5xx |
| profile 快照一致性 | 编排器 | finding 记录的 `profile_version` 与链中使用的不一致 → 编排器负责 |
| 链中数值正确 | 生成方 + 计算器 | 出现实数 → 生成方；占位符解析错 → 计算器 |
| 锚点可回验 | 生成方（产出）+ 回验器（判定） | 字段缺 → 生成方；字节比对误判 → 回验器 |
| 回验失败后是否可展示 | 编排器 | 任何降级展示 → 编排器负责 |
| 台账不可篡改 | 台账服务 | 能被 UPDATE → 台账服务 |
| 缓存是否命中旧索引 | 缓存服务 + 编排器 | key 缺 `index_version` → 缓存；传错版本 → 编排器 |
| 出域合规 | 网关 | 违规载荷被放行 → 网关；未标 `egress_class` 仍调用 → 调用方 |
| 供应商侧状态改变 | 采购与网关配置 | 供应商留存或微调 → 网关配置方，不是供应商 |

**按谁的口径判**：一律按本文件与《接口》的定义判，不按某一侧的实现现状判。实现与契约不一致时，以契约文本为准并开缺陷，不得「以跑通的为准」改契约。

## 第 3 章 逐契约定义

### 3.1 CT-1 检索服务契约

**请求（编排器 → 检索）**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `query` | 字符串 | 是 | 1 到 2000 字，已改写后的最终查询 |
| `channels` | 数组 | 是 | 子集 `dense` / `sparse` / `sql`，至少一个 |
| `acl_scope` | 数组 | 是 | 不得为空数组以外的缺失；由网关注入 |
| `index_version` | 字符串 | 是 | 必须为 active 版本 |
| `top_k` | 整数 | 是 | 默认 20，上限 100 |
| `provision_hint` | 字符串 | 否 | 查询中含条款编号时传入，命中即置顶 |
| `filters` | 对象 | 否 | `corpus_type`、`effective_at`、`lang` |

**响应**

| 字段 | 类型 | 说明 |
|---|---|---|
| `candidates` | 数组 | 每项含 `chunk_id`、`provision_id`、`score`、`channel`、`page_no`、`text` |
| `fused` | 数组 | RRF 后顺序，含 `rrf_score` 与来源通道 |
| `reranked` | 数组 | 条款级重排后的 Top-5，含 `provision_id` 聚合的 chunk 列表 |
| `sparse_disabled` | 字符串 | 为空表示启用；值为 `lang_mismatch` 表示跨语言关闭 |
| `empty_reason` | 枚举 | `no_match` / `acl_filtered` / `index_not_active` |

**三条硬规则**

1. `acl_scope` 缺失 → `ACL_SCOPE_MISSING`，不查库。
2. 跨语言（`query.lang != chunk.lang`）时稀疏通道必须关闭并写 `sparse_disabled=lang_mismatch`；不得以「得分为 0」静默混入融合。
3. 重排必须在条款级聚合后执行；同一条款最多占 1 个 Top-5 名额。

**失败**：单通道失败不整体失败，返回其余通道并在 `channel_errors` 中标明；三通道全失败才返回 `UPSTREAM_TIMEOUT`。

### 3.2 CT-2 生成服务契约

> **范围说明（2026-11-10 收窄）**：`task_type=formal`、`PROFILE_MISSING`、`SUPPLY_NOT_ALLOWED`、`signoff_eligibility` / `draft_only` 与 `verdict` 判定语义为产品范围外·二期候选，原文保留不执行；QA 生成、`calc://` 占位符、`CONTEXT_BUDGET_EXCEEDED` 保留执行。

**请求**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `task_type` | 枚举 | 是 | `qa` / `formal` |
| `supply` | 枚举 | 是 | `self_hosted` / `managed_pinned` / `managed` |
| `inference_scope` | 枚举 | 是 | `local_single_gpu` / `cluster`；一期只有前者 |
| `chain_input` | 对象 | 是 | 条款锚点、profile 快照、候选证据 |
| `max_steps` | 整数 | 是 | ≤ 8 |
| `numeric_mode` | 枚举 | 是 | 固定 `placeholder_only` |
| `context_budget` | 整数 | 是 | 由生成方按 `model_snapshots.ctx_limit` 回填，调用方不得自行声明 |
| `answer_lang` | 枚举 | QA 必填 | `zh` / `en`；由编排器据此选择答案模板与引用侧，`formal` 忽略 |

**响应**

| 字段 | 类型 | 说明 |
|---|---|---|
| `steps` | 数组 | L / A / E / C / J 五段，每段含 `step_no`、`type`、`payload`、`anchors` |
| `verdict` | 枚举 | 四态之一 |
| `signoff_eligibility` | 枚举 | `signable` / `draft_only`，见硬规则 5 |
| `rounds` | 整数 | 实际生成轮数（`local_single_gpu` 下通常为 3） |
| `model_fingerprint` | 字符串 | 供应商标识或自建权重哈希 |
| `prompt_version` / `prompt_hash` | 字符串 | 必填 |
| `tokens_in` / `tokens_out` | 整数 | 用于配额对账；超预算必须报错而非截断 |

**硬规则**

1. `task_type=formal` 且 `supply=managed` → `SUPPLY_NOT_ALLOWED`，在编排器侧就要拦，不得下发到生成服务。
2. 生成方不得在 `payload` 中输出实数；只允许 `calc://{calc_id}` 与白名单内的编号、页码、年份。
3. 任一步缺 `anchors` → 该步非法，生成方须重生成一次；再失败返回 `ANCHOR_INVALID`。
4. 生成方不负责判定 verdict 是否合理，只负责按链结构输出；裁定与回验在 CT-3。
5. **`signoff_eligibility` 由生成方按 `inference_scope` 与已登记的判定一致率派生，调用方不得覆盖。** `local_single_gpu` 且该 `model_snapshot_id` 的实测判定一致率 < 0.85 时返回 `draft_only`；台账据此拒绝签署（CT-8 硬规则 6）。这一项是服务端事实，不是前端开关。
6. **`local_single_gpu` 下必须分段生成，禁止单次投喂全链。** 任一请求的 `tokens_in` 超过 `model_snapshots.ctx_limit × 0.85` 时返回 `CONTEXT_BUDGET_EXCEEDED`，不做静默截断——截断会造成证据片段被切掉一半而锚点仍指向它，回验器抓不到这种缺失。轮间只传结构化中间态。
7. **QA 答案语种由编排器单一决定，不在一条回答内混排。** `answer_lang=zh` 时引用锚点必须指向中文显示层块（`doc_id` 为中译本），`answer_lang=en` 时指向英文原版块；两种模式下 `translations[]` 均为 `[]`。中文模式命中条款缺中文译块时，只能返回「无中文译文，请切换英文版」类拒答并记 `zh_unavailable:<provision_id>`，不得降级回英文原文，也不得表述为检索为空。`answer_lang` 进入幂等指纹：同一 `Idempotency-Key` 改语种重放按新请求处理，指纹不符返回 `IDEMPOTENCY_CONFLICT`。

**超时**：单轮 90s，整体 300s。超时不重试，返回 `UPSTREAM_TIMEOUT` 且不返回半条链。

**显存协作规则**：本契约的调用方（编排器）必须在调用前确认生成模型已就绪；未就绪时编排器负责触发显存切换并等待，切换耗时不计入生成方超时。**生成方不得自行卸载嵌入或重排模型**——显存编排只有一个责任方，否则会出现两个服务交替卸载对方、互相抖动。

### 3.3 CT-3 锚点回验契约

**请求**：`finding_draft`（含 steps、verdict、anchors）、`source_snapshot`（doc_id + version_no + file_hash）。

**响应**：`result` ∈ {`pass`, `fail`}，`failures` 数组含 `anchor_id`、`reason` ∈ {`anchor_missing`, `provision_not_found`, `span_mismatch`, `page_mismatch`, `calc_not_allowed`}、`expected`、`actual`。

**硬规则**

1. 回验只读原件与数据库，**不得调用生成模型**。
2. 比对按 Unicode 码点切片后逐字节比较，不做空白归一、不做全半角转换、不做大小写折叠。
3. 任一项失败 → `fail`，编排器必须整链作废；回验器不提供「部分通过」。
4. 回验器不得修改入参，不得「顺手修正」`span_text`。
5. **QA 引用走同一口径**：`task_type=qa` 不产生 finding，编排器按单条引用调用回验，请求为 `ref_id` + 锚点最小字段，响应沿用 `pass` / `fail` 与 `failures[]`。问答引用不得另建一套宽松校验。
6. QA 引用落库时，`span_text` 只进 `cot_chains.anchors_json`；`payload_json` 只存定位字段、`answer_mode` 与答案模板，不存条款原文。

### 3.4 CT-4 索引构建契约

**请求**：`doc_id`、`version_no`、`chunks`、`embedding_model`、`embedding_version`、`config_hash`。

**响应**：`index_version`、`state`、`chunk_count`、`milvus_count`、`active_at`。

**两阶段提交**

| 阶段 | 动作 | 失败处理 |
|---|---|---|
| 一 | SQLite 写 `documents` 与 `chunks`，状态 `pending` | 回滚事务 |
| 二 | Milvus 写入并回查计数 | 不一致 → `failed`，SQLite 侧标失败原因 |
| 三 | `indexed` → 抽样 20 条回查 → `active` | 回查失败 → `rolled_back` |

**硬规则**：`milvus_count` 必须等于 `chunk_count`；抽样回查的 20 条必须 `chunk_id` 与 `provision_id` 全部一致。任何一项不等即不得 active。

**显示层构建（`index_mode=display_only`）**

| 项 | 规则 |
|---|---|
| 适用 | 有独立原件、只用于引用对照或展示的语料（如中文译版），不得被检索命中 |
| 落库 | 只写 SQLite `documents` / `chunks` 与对象存储页文本；`documents.index_status='display_only'`，`chunks.index_version='display_only'` |
| 计数 | `milvus_count` 固定为 0，**不适用**「必须等于 `chunk_count`」；该版本从未写入向量库，故不存在两阶段提交的计数一致问题 |
| 检索可见性 | 检索服务必须按 `index_status <> 'display_only'` 与 `index_version <> 'display_only'` 双重排除；混入即视为契约违约 |
| 前置校验 | 仍须通过六项元数据校验与解析质量闸门，不因「只作显示」而放宽 |
| 责任 | 显示层版本被检索返回，由检索服务负责；显示层未落库导致引用无法展示，由离线构建器负责 |

**双语配对（跨 CT-4 与 CT-3）**：`pair_id` 在两侧都入库后由离线脚本回写 SQLite，属于可重入的后置步骤。检索与回验都不读 `pair_id`；引用展示按 `pair_id` 反查中文块后，仍须逐条走 CT-3 的单条回验，未通过的对照不得展示。

### 3.5 CT-5 语义缓存契约

**key 组成**（缺一即 `CACHE_KEY_INCOMPLETE`）：`sha256(归一化查询)` + `index_version` + `acl_scope` 排序后哈希 + `profile_version` + `prompt_version`。

**值**：`kind` ∈ {`retrieval`, `qa_answer`}，`payload`，`created_at`，`hit_count`。**不得存 `verdict`、`cot`、任何 C 类数值。**

| 规则 | 内容 |
|---|---|
| 命中阈值 | 余弦 ≥ 0.95，且必须记录实际相似度 |
| 命中标注 | 响应必须带 `cache_hit=true` 与 `cache_key`，前端须显示 |
| 失效 | 任一 key 分量变化即不命中；索引切换为全量失效 |
| 缓存穿透 | 空结果缓存 60 秒，避免重复打空 |
| 一致性 | 不要求与索引强一致，靠 `index_version` 隔离 |

### 3.6 CT-6 模型供给契约

**请求**：`purpose`（`embed` / `rerank` / `generate` / `ocr` / `asr` / `vision`）、`supply`、`inference_scope`、`payload`、`egress_class`、`purpose_task`（`qa` / `formal`）。

`egress_class` 枚举固定四值，不接受自定义：`text_query` / `page_image` / `audio` / `vl_image`。其中 `page_image` 专指整页图像（OCR 用），它的出域审批规则不在本契约，见 CT-11。

| 规则 | 内容 |
|---|---|
| 供给校验 | `purpose_task=formal` 且 `supply=managed` → 拒绝，不回退 |
| 作用域校验 | `supply=self_hosted` 时 `inference_scope` 必填；`managed` / `managed_pinned` 时该字段须为 `cluster`，与自建本地互斥 |
| 显存归属 | `inference_scope=local_single_gpu` 的请求只能落到本机推理进程；网关不得把同一张卡上的请求并发放行，超出的按队列排队并回传 `queue_position` |
| 出域标记 | `egress_class` 缺失或为 `forbidden` → 拒绝 |
| 版本记录 | 响应必须回传 `model_fingerprint`；`managed_pinned` 还须回传 `model_version` 与 `contract_id` |
| 零留存 | 请求头带 `X-No-Retention: true`；供应商不支持则不得使用该档 |
| 关闭能力 | 请求体显式关闭 memory、fine-tune、session continuity、personalization |
| 限流 | 429 时按指数退避，最多 3 次；仍失败则任务 `pending_retry` |
| 责任 | 供应商侧状态改变导致的数据留存，由网关配置方负责，不推给供应商 |

**本机推理的四条附加责任划分**（只有 `inference_scope=local_single_gpu` 时生效）：

| 项 | 责任方 | 判据 |
|---|---|---|
| 显存切换（加载/卸载模型） | 编排器 | 网关只转发，不判断显存状态；切换失败由编排器返回 `GPU_UNAVAILABLE` |
| OOM 归因 | 编排器 | 记录崩溃前的 `resident_models[]`、`ctx_tokens`、`batch_size`；缺任一项视为未提供证据，缺陷挂「待查」而非「已定位」 |
| 上下文超限 | 生成方 | 超 `ctx_limit × 0.85` 直接拒绝，不截断（见 CT-2 硬规则 6） |
| 并发控制 | 网关 | 本机并发固定为 1；第 2 个请求进入队列，不得并发下发导致双份 KV cache 撑爆 |

### 3.7 CT-7 结构化查询契约

**请求**：`question`、`acl_scope`、`allowed_views`（服务端固定，不接受客户端传入）。

**响应**：`sql`（仅用于审计回放）、`rows`（≤200）、`columns`、`truncated`。

| 规则 | 内容 |
|---|---|
| 账号 | 独立只读账号，仅授予视图 SELECT |
| 白名单 | `v_provisions`、`v_pnp_mappings`、`v_disclosure_items`、`v_composites_meta` |
| 禁止表 | `firm_profiles` 明文、`calc_results`、`findings`、`cot_chains`、`audit_logs` |
| 行数 | `LIMIT 200` 由服务端强制追加，不依赖模型生成 |
| 超时 | 5s，超时返回 `UPSTREAM_TIMEOUT`，不重试 |
| 注入 | 生成 SQL 后必须先过语法白名单校验（仅 SELECT、无子查询写、无 PRAGMA） |
| 失败 | `SQL_GUARD_REJECTED` 时不返回任何行，不得「尽量给一点」 |

### 3.8 CT-8 台账写入契约

> **范围说明（2026-11-10 收窄）**：签署、dispute、finalize、ledger 导出为产品范围外·二期候选，原文保留不执行；finding / cot_chains 同事务写入、哈希链、触发器禁 UPDATE/DELETE 保留执行（QA 问答链落同一套 cot_chains 表）。

**请求**：`finding`（含 verdict、anchors、calc_ids、profile_version、model_snapshot_id）、`idempotency_key`、`row_version`。

| 规则 | 内容 |
|---|---|
| 追加 | `cot_chains` 只 INSERT；`findings` 结论变更新增行并标 `superseded_by` |
| 哈希链 | 每行 `self_hash = sha256(prev_hash + 规范化字段序列)`；规范化规则固定为字段名字典序 + `=` 连接 |
| 权限 | 应用账号无 UPDATE / DELETE；触发器二次拦截 |
| 并发 | 签署用 `row_version` 乐观锁；冲突 409 |
| 事务 | finding 与其 cot_chains 同事务写入，任一失败全部回滚 |
| 签署 | 必须校验签署人 ≠ 撰写人；`finalize` 必须校验角色为 Approver |
| 签署资格 | **`signoff_eligibility=draft_only` 的 finding 拒绝任何签署动作，返回 `DRAFT_NOT_SIGNABLE`。** 该字段由生成方派生（CT-2 硬规则 5），台账只读不回写。不得以「人工已复核」为由提供绕过参数——绕过参数一旦存在，`draft` 机制就等于没有 |
| 资格变更 | 升级模型快照并重跑后产生的新 finding 才可签署；旧 finding 保持 `draft` 并标 `superseded_by`，**不得原地改资格** |
| 失败 | 哈希链断裂 → 拒绝写入并告警，不得跳过 |

### 3.9 CT-9 文档与语料管理契约

**上传**

| 规则 | 内容 |
|---|---|
| 幂等键 | `sha256(文件字节)`；重复上传返回已存在的 `doc_id` 与版本，不重复入库 |
| 必填元数据 | `corpus_type`、`dept`、`clearance`、`doc_type`、`effective_from`，缺一即 400 |
| 版本判定 | 同 `doc_id` 且哈希不同 → 必须 `version_no + 1`；哈希相同但版本不同 → 拒绝 |
| 状态 | `uploaded` → `parsed` → `published`；`parsed` 之前不可发布。受理接口只推进到 `uploaded`，后续迁移由写队列异步完成 |
| 受理方式 | 上传接口只做元数据校验、恶意文件闸门与原件落盘，通过即返回 `202` 与入库任务号；解析、切分、建索引由单写队列串行执行，状态经任务查询接口读取。云通道关闭或队列积压时写请求排队而不是同步失败 |
| 失败语义 | 队列处理失败 → `documents.status=failed`，任务终态 `failed` 且 `business_code` 记失败原因（OCR 失败统一 `ocr_failed`）；不得静默丢单 |
| 原件 | 内容寻址落对象存储，路径由哈希决定，不按文件名 |

**发布**

| 规则 | 内容 |
|---|---|
| 二次确认 | 发布须带一次性 `confirm_token`（由预览接口签发，5 分钟有效） |
| 哈希复核 | 发布时重算原件哈希，与登记不一致 → `DOC_HASH_MISMATCH`，不得发布 |
| 索引联动 | 发布成功才触发 CT-4 构建；构建失败不回滚发布状态，标 `index_failed`。`index_mode=display_only` 的文档只触发显示层构建，见 CT-4 |
| 下架 | 软删：`deleted_at` 置位，检索不可见，原件与索引保留 30 天后清理 |
| 并发 | 同 `doc_id` 并发发布两个版本，后到者 409（`version_no` 乐观锁） |

**映射**

1. `suggest` 接口只返回建议，**不写库**，响应含 `suggestion_id` 与置信度。
2. 写库必须人工确认，`confirmed_by` 与 `confirmed_at` 必填；无确认人的映射不计入覆盖率。
3. 条款版本变更后，受影响映射标 `stale`，不得自动重新确认。

**责任**：上传方保证元数据真实；服务端保证哈希、ACL 与索引联动；映射确认人保证语义正确——系统不判定语义，只记录谁确认的。

### 3.10 CT-10 配置与运维契约

**模型登记**

| 规则 | 内容 |
|---|---|
| 只增不改 | `model_snapshots` 无 UPDATE；权重或版本变化必须新增行 |
| 阻断条件 | `weight_hash` 变化而 snapshot 未升 → 拒绝发布 finding |
| 禁热更新 | 登记后须显式 `activate`，激活动作写审计 |
| 供给档 | 登记时必填 `supply`；`formal` 只接受 `self_hosted` 与 `managed_pinned` |

**通道开关**

1. 关闭云通道 → 立即生效，在线生成转 `pending_retry`，只读接口保持可用。
2. 开启云通道须校验准入项齐备（零留存条款、版本冻结承诺、DLP 规则已加载），缺项拒绝开启。
3. 开关动作必须二次确认并写 `audit_logs`，不接受静默变更。

**备份与演练**

| 项 | 要求 |
|---|---|
| 快照 | SQLite 每 5 分钟一次，保留 7 天；恢复点须可用于重放 |
| 演练 | 每季度一次，须包含「由原件重建索引并跑召回基线」 |
| 记录 | 演练结果写审计；未演练的备份不计入 RTO 达标 |

**评测**

`eval_results` 必须携带 `config_hash`（切分版本 + 嵌入版本 + 重排开关 + prompt 版本）；缺配置的结果不得作为发布依据。

**责任**：运维方保证演练真实执行（有可核对日志）；变更发起方保证二次确认与审计留痕；配置错误导致的判定漂移由变更发起方负责。

### 3.11 CT-11 云端 OCR 出域契约

OCR 是本期唯一会把**整页图像**送出边界的动作，责任必须单独定死。它不归 CT-6 管，因为发起方是离线构建器而不是在线网关，出事时的追责链完全不同。

**请求**

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `doc_id` / `version_no` / `page_no` | 字符串 / 整数 / 整数 | 是 | 三元组唯一确定一页，缺一即拒 |
| `image_bytes` | 二进制 | 是 | 已按 `crop_box` 裁边后的图像；原始整页不得直接发送 |
| `crop_box` | 对象 | 是 | `{x0,y0,x1,y1}`，相对原始页面的坐标；用于复现与审计 |
| `corpus_type` | 枚举 | 是 | `A_spec` / `B_internal`；**`C_ledger` 一律拒绝** |
| `approval_ref` | 字符串 | 条件必填 | `B_internal` 时必填，指向已落档的审批记录；`A_spec` 可空 |
| `provider` | 枚举 | 是 | `aliyun` / `tencent`；切换供应商时下游无感 |
| `idempotency_key` | 字符串 | 是 | `sha256(doc_id+version_no+page_no+crop_box+provider)` |

**响应**：`OcrResult`，字段固定为 `blocks[]`（每块含 `text`、`bbox`、`block_type` ∈ `text`/`table`/`figure`/`header`/`footer`）、`page_width`、`page_height`、`provider`、`provider_request_id`、`confidence_avg`、`elapsed_ms`。

**三条硬规则**

1. **无审批即拒。** `corpus_type=B_internal` 且 `approval_ref` 为空 → `OCR_APPROVAL_MISSING`，不发送请求、不写 egress_logs 的「已发送」状态。**禁止「先发后补审批」**——补批在事后永远补得出来，那样审批就是形式。
2. **`C_ledger` 永久拒绝，无兜底路径。** 返回 `OCR_FORBIDDEN_CORPUS`，并提示转人工录入。**不得因为「没有本地 OCR」而放宽这条**——放宽的代价是把「台账永不出域」这条产品底线变成一句空话。
3. **结果归一。** 两家供应商的字段结构不同，必须在网关侧归一为同一个 `OcrResult`。下游只认 `OcrResult`，不得出现 `if provider == 'aliyun'` 的分支散落在解析器里——那会让换供应商变成全链路改造。

**失败语义**：`upstream_error` → 换第二家供应商重试 1 次；两家都失败 → 该页标 `ocr_failed` 并进入人工复核队列，**不得静默跳过该页**（跳过会造成该条款证据缺失，而系统会把它误判为「条款无要求」）。

**状态与并发**：同一 `idempotency_key` 重复请求返回缓存结果，不重复计费、不重复出域。同一页的并发请求合并为一个，后到者等待首个结果。

**责任划分**：

| 出事场景 | 责任方 |
|---|---|
| 未审批的 B 类页面被发出 | 离线构建器（未校验 approval_ref）；网关负连带（未拦截） |
| 裁边没裁掉盖章区，敏感信息随图像出域 | 离线构建器（crop_box 计算错误） |
| 供应商留存了图像 | 网关配置方（未落实零留存条款）；采购方（合同缺条款） |
| 换供应商后解析结果变差、锚点漂移 | 解析器维护方（未重跑抽检） |
