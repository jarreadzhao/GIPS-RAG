## 1. 变更缘由

CHG-20261110-10 记录三条未闭合项，本次按「补实现 / 转整改 / 划边界」逐条处置：

| 项 | 原状 | 裁定 | 依据 |
|---|---|---|---|
| AC-74 8 小时浸泡 | 只跑 10 分钟，判「未达成」 | **转上线后整改**，不补测、不改判据 | 补测需连续 8 小时占用交付机，与当期交付节奏冲突；判据保持原文，缺口进「上线后整改」清单并写明责任人 |
| AC-75「写请求进入排队」 | 上传接口同步解析，云通道关闭时直接 504，无异步队列 | **补异步写队列**：上传只受理，解析/切分/建索引入队串行执行 | 判据原文即要求排队；改判据属「把判据改成免责声明」，不做 |
| AC-76 供应商核查 | M5 要求出证据，CT-6/CT-11 写云端出域与调用链本期不执行 | **以上游为准并写明边界**：本期只核查供应商侧配置证据，云端调用链随二期 | 派生链单向；边界说明不降低判据，配置缺证据仍判不通过 |

AC-75 的「排队」需要一个任务载体。增量新建 `ingest_tasks` 表要重写状态机、查询接口与补一套生命周期，而
`review_tasks` 已经具备 `created/running/succeeded/failed` 状态与查询接口；因此**复用 `review_tasks`，
新增 `task_type='ingest'`**，不建新表。

## 2. 处置

### 2.1 规格回写（PRD → 契约 → 接口 → 验收）

| 层 | 改动 |
|---|---|
| PRD | R-6 补「降级期间写请求进入队列排队，不得同步失败丢单」；2.5.3 降级行同步写明上传入库先受理后排队、失败落码转人工复核 |
| 契约 | CT-9 上传新增「受理方式」「失败语义」两行；状态行注明受理接口只推进到 `uploaded`，后续迁移由写队列异步完成 |
| 接口 | API-18 响应由「201 + 同步完成结果」改为「202 + `task_id` + `queue_position`」，重复上传改为 200 + `duplicate=true`，补处理失败语义；API-5 补 `task_type=ingest` 的返回结构与排队口径 |
| 验收 | AC-75 增「判定口径」段（202 + 任务号 + 终态失败码为证据）；M5 增「AC-76 边界」段（只核查供应商侧配置证据，云端调用链随二期，判据不降） |

**没有删除或改写任何 R / CT / API / AC 的定义行**，四项判据阈值一字未动。

### 2.2 代码

| 文件 | 改动 |
|---|---|
| `db/schema.sql` | `review_tasks.task_type` 的 CHECK 增加 `ingest`，并注明统计必须按 `task_type` 过滤 |
| `app/core/db.py` | 新增 `_prepare_review_tasks_migration` / `_finish_review_tasks_migration`：CHECK 不能原地改，按 documents 迁移的同一套路重建表，`legacy_alter_table=ON` 保住 findings / cot_chains 外键指向 |
| `app/ingest/worker.py`（新增） | `IngestScope` 载荷、`run_ingest()`（原同步管线的抽离）、`IngestWorker`（单线程写队列）；启动时把 `created` 任务重新入队、`running` 任务判 `WORKER_RESTARTED` 失败；失败统一写 `business_code`（OCR 失败记 `ocr_failed`）并把文档置 `failed` |
| `app/api/documents.py` | 上传只做校验、恶意文件闸门、原件落盘与文档/任务入库，返回 202；解析与建索引移出请求线程 |
| `app/api/reviews.py` | `GET /reviews/{task_id}` 对 ingest 任务返回 `document` 与入库队列位次，不再混用 GPU 队列计数 |
| `app/main.py` | `AppContext` 增加 `ingest`；lifespan 启动时拉起写队列、退出时停止 |
| `tests/test_upload_pipeline.py` | 改为断言 202 → 轮询任务终态；新增「云通道关闭时仍受理、任务终态 `failed` + `ocr_failed`、`egress_logs` 记 `egress_disabled`」一条 |

### 2.3 实测

- 全量测试：`pytest -q` → **156 passed + 36 skipped，0 failed**（新增 1 条，原 155 条无回归）。
- AC-75 重跑（`GIPS_EGRESS_ENABLED=false`，需 OCR 的扫描件）：`POST /documents` 返回 **202** 与 `task_id`；
  任务先 `created` 后终态 `failed`、`business_code=ocr_failed`；`documents.status=failed`；
  `egress_logs` 记 `state=failed`、`dlp_verdict=egress_disabled`，无载荷出域。

## 3. 规格判定

按「这次改动会不会让一个本来通过 AC 的实现变成不通过，或让不通过的行为变成通过」：

- **会**。改动前 AC-75 因「无异步队列」判部分满足；实现后「写请求进入排队」可复现通过，同时 AC-74 转整改、AC-76 划边界也改变了判定书写的口径。因此四份齐升 v1.8 并开本单。
- **未降低标准**：AC-75 仍要求只读可用、排队、30 分钟内降级；AC-74 判据原文保留，缺口转上线后整改；AC-76 的配置关闭项仍以可核对证据为准。

## 4. 下游影响

- **契约**：CT-9 补齐受理与失败语义；CT-6 / CT-11 不动（其「云端不执行」的表述正是 AC-76 边界的上游依据）。
- **接口**：API-18 响应码与字段变化（201 → 202，新增 `task_id` / `queue_position` / `status_url`），API-5 新增 ingest 返回；仓库内唯一调用方 `tests/test_upload_pipeline.py` 已同步，前端上传页仍为占位、无调用。
- **验收**：AC-75 判定口径与 AC-76 边界落文字；AC-74 的「转上线后整改」写进 `reports/交付清单.md` 的未决项与 `reports/压测报告.md`，不写进 AC 判据。
- **codemap**：新增 `app/ingest/worker.py` 一行，映射 R-6 / AC-75。

## 5. 遗留

- 统计债务：`review_tasks` 混入 ingest 后，任何「审查任务数 / 完成率」口径必须加 `task_type='qa'/'formal'` 过滤；已在 schema 注释与本单记录，后续做统计报表时强制。
- `documents` 表无 `ocr_approval_ref` 列，审批引用存在任务 `scope_json` 里；若二期需要按文档审计审批，再补列（走新 CHG）。
- AC-74 8 小时浸泡、AC-72 完整工作日、AC-78 抓包：转上线后整改，责任人与截止日期见 `reports/交付清单.md`。
