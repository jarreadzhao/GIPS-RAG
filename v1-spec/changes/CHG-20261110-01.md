## 1. 变更缘由

两处都是「规格写错、代码是对的」，不涉及任何阈值与判定口径：

1. **GAP-CHG-01（CHG-20261109-01 第 5 节已记录）**：`契约.md` 第 2 章标题写「八份契约共同适用」，而第 1 章清单实为 11 份（CT-1 至 CT-11）。属于新增 CT-9～CT-11 时漏改标题的计数残留。
2. **评测集产物路径**：`验收标准.md` M1 产物写 `eval/golden-v1.jsonl` / `eval/dev-v1.jsonl`（同目录两文件），而 `app/eval/dataset.py` 强制 `eval/golden/` 与 `eval/dev/` 两个目录物理分离，同目录或 golden 目录内嵌 dev 一律抛 `EvalGuardError`。代码的做法是为堵「dev 调完提示词直接跑 golden」而设计的，规格的写法是旧口径的残留。按项目规则「规格写错 → 回改上游」，此处改规格。

## 2. 逐文件的实质改动

| 文件 | 位置 | 改动 |
|---|---|---|
| 契约.md | 第 2 章标题 | 「八份契约共同适用」→「11 份契约共同适用」（与第 1 章清单计数一致） |
| 验收标准.md | M1 产物表两行 | `eval/golden-v1.jsonl` → `eval/golden/golden-v1.jsonl`；`eval/dev-v1.jsonl` → `eval/dev/dev-v1.jsonl`；golden 行由「冻结的 200 条验收集」改为「冻结的自生成查询集（≥200 条）」，并注明标注者为规则生成器而非模型——自生成口径的 gold 由条款自身派生，没有模型标注器可记录 |
| PRD.md | 文档头 | 版本 v1.2 → v1.3，变更单换本单；**正文一字未动** |
| 接口.md | 文档头 | 版本 v1.2 → v1.3，上游版本 v1.2 → v1.3，变更单换本单；**正文一字未动** |

**为什么四份都升版、且上游版本全部跟到 v1.3**：`spec_link.py` 第 [6] 项要求四份「变更单」字段同号。给契约开新单，就必须同时改另外三份的「变更单」字段；而 `spec_gate.py` 第 [2] 项要求「文件被改过就必须版本前进」，第 [4] 项要求下游「上游版本」严格等于 PRD 当前版本。三条叠加的结果是四份一起升 v1.3、三份上游版本跟到 v1.3。这不是把无关文件拉下水，是机检对「一次变更一个单号、版本链不得断」的强制表达；项目规则里「只改契约正文时上游版本不变」那一行，只在 PRD 版本未变时成立，本单因单号对齐而连带改了 PRD 文档头，故不适用。实质正文改动仍只在契约与验收两处。

## 3. 下游影响（三份逐条回答，无影响也要写理由）

- **契约**：第 2 章标题的契约份数由八改十一。第 2 章正文（六块通用规则）一字未改；无字段、无错误码、无超时口径变化。
- **接口**：无影响。接口依据的是 CT-1 至 CT-11 的具体条目，标题里的份数不构成任何接口约束；本次仅换单号与版本号。
- **验收**：评测集路径改为目录隔离写法，与 `app/eval/dataset.py` 的守卫一致。**不新增、不删除、不放宽任何 AC**；AC-13 / AC-14 / AC-82 的判定阈值仍为 Recall@5 ≥ 0.92、两次差值 ≤ 1 个百分点。

## 4. 规格影响判定

按项目规则的一句话判据：这次改动会不会让一个本来通过 AC 的实现变成不通过，或让一个本来不通过的行为变成通过？

- 契约标题：不会。它不参与任何机检阈值，只影响人读。
- 评测集路径：不会。改动方向是让规格与代码现有守卫对齐；原先按规格写在同目录的实现，本来就会被 `EvalGuardError` 拒绝，属于「规格描述了一个必然失败的实现」。

结论：**行为判定影响：无。** 但因正文有改动，按规程仍须升版并开单，不得静默修改。
