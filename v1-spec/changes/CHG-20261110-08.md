# CHG-20261110-08 DEF-Q0-03 修复：review_tasks 增加 business_code 列并由编排器写入

## 1. 变更缘由

DEF-Q0-03（P2）：`RETRIEVAL_EMPTY` 业务码不落库，只能从链形状反推，拒答记录无法按类型筛选与统计。解除条件：`review_tasks` 增加 `business_code` 列并由编排器写入。

修复前的事实链：编排器在检索为空时（AC-45）返回 `ReviewOutcome.business_code="RETRIEVAL_EMPTY"`，该码只存在于进程内响应体中；`_finish_task()` 终态落库时只写 `status` 与 `finished_at`，业务码随进程结束丢失。事后想统计「多少任务因检索为空拒答」，只能解析 `cot_chains` 的链形状（L、A 两步后无 E/C），既脆又慢。

## 2. 处置（代码）

| 文件 | 改动 |
|---|---|
| `db/schema.sql` | `review_tasks` 增加 `business_code TEXT` 可空列（注释：业务态码如 RETRIEVAL_EMPTY，终态时由编排器写入；NULL=无业务码） |
| `app/core/db.py` | 新增 `_add_review_tasks_business_code()` 迁移：`PRAGMA table_info` 判列缺失后 `ALTER TABLE ... ADD COLUMN`（纯加列无 CHECK 参与，无需重建表）；幂等；挂在 `executescript(sql)` 之后、cot_chains 迁移之前 |
| `app/reason/orchestrator.py` | `_finish_task()` 增加可选参 `business_code`，UPDATE 改为 `business_code=COALESCE(?, business_code)`——只在有值时写入，不覆盖已有码；检索为空分支的 `_finish_task(task_id, "succeeded")` 调用改为传入 `outcome["business_code"]` |
| `tests/test_m2_review.py` | `test_retrieval_empty_refuses` 增加 DB 层断言：任务终态后 `review_tasks.business_code == "RETRIEVAL_EMPTY"` 且 `status == "succeeded"` |

- 老库迁移：重启后端后 `PRAGMA table_info(review_tasks)` 确认 `business_code` 列已存在于 `var/gips.db`；
- 后端：`/healthz` → ok（version 0.1.0-M2），老库数据未受影响。

## 3. 规格判定

### 3.1 规格影响：无（判定过程）

按项目规则第二节的判据过一遍：

> 这次改动，会不会让一个本来通过 AC 的实现变成不通过，或者让一个本来不通过的行为变成通过？

不会。这是一次纯增量修复：

1. **不翻转任何 AC**。AC-45（检索为空拒答）的判定对象是「拒绝行为本身」（不用先验知识补、返回拒答），落库业务码是可观测性增强，AC-45 的操作与判定语句无需变化。
2. **API-5 响应新增字段属兼容变更**。`GET /reviews/{task_id}` 用 `SELECT *` 透传行数据，响应体自动多出 `business_code` 字段（可空，默认 null）。契约 2.5 已约定「新增字段必须可选且有明确默认值；客户端须容忍未知字段」，本次满足。
3. **为什么不本次回写接口.md**：`spec_link` 第 [6] 项机检要求四份文件的变更单号一致；为单个响应字段单独升接口.md 会让其余三份的变更单指针失配，触发四件套全链升版。字段级文档回写推迟到下一次接口文档修订（第 3 步 M4 或第 5 步收口前）合并处理，届时一并升版。此判定记录在案，不属于「改判据迁就代码」——AC 判据一字未动。

## 4. 下游影响

- **契约**：不动。CT-2 定义的是生成服务请求/响应，业务码落库在编排器侧台账，不跨服务。
- **接口**：API-5 响应新增 `business_code`（可空），按契约 2.5 兼容新增；字段级文档下次接口修订时补入（理由见 3.1 第 3 条）。
- **验收**：不动。AC-45 判据不变；DEF-Q0-03 解除后，Q0 审计报告第 4 节的缺陷状态应在下次重跑审计时更新为「已解除」。

## 5. 遗留

- `reports/Q0-引用回链与越界审计.md` 中 DEF-Q0-03 状态标注为「已解除」的更新，待下次审计重跑时随报告一起改（避免为改一行状态单独动报告）。
- 历史 12 条旧 QA 任务（答案未落库无法核验，见审计 8.3）的 `business_code` 恒为 NULL，属预期：迁移只加列不回填。
