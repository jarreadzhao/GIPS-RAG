## 1. 本次变更做了什么

按参考技术栈（单体 FastAPI + Milvus 稠密/稀疏 + SQLite + Redis + 本地对象存储 + DeepSeek / DashScope / 阿里云 OCR·ASR / Qwen-VL + Langfuse / Prometheus）从零建立 GIPS 合规审查 RAG 的四份规格文档。

产品定位与 CoT 机制沿用 `gips-review-rag/PRD-v0.2.md`；架构按该技术栈重写，并对参考架构补齐七处缺口（ACL、引用锚定与回验、缓存查/写两段、意图分支、text-to-SQL 与融合、离线打标/增量/质量闸门、离线评测）。

## 2. 语义影响分析（机器查不出的部分）

| 变更 | 影响了什么语义 | 需要人工确认的点 |
|---|---|---|
| 关系库改为 SQLite 主选 | 旧版明确「不用 SQLite」，理由是并发签署 | 一期并发假设为 8 人 / 20 会话；若部署到多业务线，8.3 的迁移触发条件必须先触发 |
| 正式审查供给分三档 | 旧版硬禁止托管 API，本版增加 `managed_pinned` 过渡档 | 这是对「固定权重」原则的有条件让步；M3 放行条件已绑定「切自建或取得续期书面意见」 |
| 新增双语 pair 原子 | 旧版未规定双语切分 | 依据实测：中文查询英文索引 R@1 0.55 / R@5 0.90，差异不显著；结论是不翻译，投多语重排 |
| 缓存拆为查/写两点 | 旧版只说「不缓存判定」 | 新增 `index_version` 进 key；重建即全量失效 |
| 新增 CT-9 / CT-10 | 文档管理与运维此前无契约归属 | 接口 38 个全部有契约归属，无悬空 API |
