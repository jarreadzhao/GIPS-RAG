## 1. 变更缘由

`scripts/ac78_capture.ps1`（CHG-20261110-13 附带产出）以 UTF-8 **无 BOM** 保存，含中文注释与中文 `Write-Host` 文本。
Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI（本机 GBK）解码，中文被打乱后引号失配，
解析期即报「语句块或类型定义中缺少右 `}`」（实测位于第 39、34、60 行），脚本一次都没跑到 `pktmon`。

后果不是「抓包失败」，而是**脚本本身不可用**：文档里写的复现命令 `powershell -ExecutionPolicy Bypass -File scripts\ac78_capture.ps1`
在任何 5.1 环境都会失败，而脚本头部恰好写着「非管理员退出码 5」，容易把语法失败误读成权限问题。

同时 `pktmon etl2txt` 的产物是 **UTF-16LE**，按 UTF-8 解析会得到大量交错 `\x00` 的「空结果」，
这一点此前没有写进脚本，第一次解析时确实踩到（解析出 0 条流）。

## 2. 处置

| 文件 | 改动 |
|---|---|
| `scripts/ac78_capture.ps1` | 文件转存为 UTF-8 **带 BOM**（内容不变）；头部补两条说明：BOM 要求、`etl2txt` 输出为 UTF-16LE |
| `reports/AC-78-抓包记录.md` | 按 2026-11-10 两轮真实抓包重写：测量条件、两轮流量统计、连接表归属、DNS 域名归属、出域台账、局限 L1～L4、判定 |
| `reports/压测报告.md` | §6 AC-78 行改为「满足（附局限）」；§7 GAP-M5-04 改为已闭合 |
| `reports/交付清单.md` | AC-78 行、GAP-M5-04、产物与复现入口、签署前确认项同步 |

抓包本身按原判据执行，**没有改 AC-78 的判据文字，也没有改任何阈值**。

## 3. 规格判定

按「这次改动会不会让一个本来通过 AC 的实现变成不通过，或让不通过的行为变成通过」：

- **不会**。改的是脚本文件编码与两行说明；`pktmon` 命令序列、QA 负载、抓包参数均未改。
- AC-78 的判定从「未满足」变为「满足」，原因是**证据补齐**（抓包真实执行），不是判据放宽：
  判据原文「抓包检查 trace 与日志外发流量，外发业务正文为 0」一字未动，阈值一字未动。
- 因此四份规格不动，本单为纯代码修正 + 报告同步。

## 4. 下游影响

- **契约**：无影响。CT 不描述抓包工具与脚本编码。
- **接口**：无影响。未改任何 API。
- **验收**：无影响。AC-78 判据未改；判定结论的更新只落在报告层（`reports/AC-78-抓包记录.md`）。
- **codemap**：`scripts/ac78_capture.ps1` 属验证脚本，未挂 R / AC 编号，不加映射行。

## 5. 遗留

- AC-78 的局限 L1～L4（128 B 截断、回环采样不全、etl 无 PID 字段、未含 OCR 出域）保留在抓包记录第 6 节，属二期增强。
- 后续新增 `.ps1` 脚本一律按 UTF-8 带 BOM 保存，避免同一坑复发。
