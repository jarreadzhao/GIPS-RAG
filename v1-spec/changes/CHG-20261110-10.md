## 1. 变更缘由

M5 表一在 CHG-20261110-06 收窄后保留 AC-71～AC-78，并要求五份产物。执行时发现五件事：

1. **AC-71A（队列可观测）没有数据来源**：`GET /reviews/{task_id}` 不返回排队位次，无法验证「位次随进度递减且与实测一致」。
2. **`GPUPool.queue_position()` 读不到真实值（真缺陷）**：该方法与 `acquire()` 共用同一把 `RLock`，且 `_waiting` 在拿到锁之后才自增——观测方要读位次必须等当前 GPU 操作结束，读到的永远是 0 或过期值。修复前采样 5 次全为 0，修复后峰值 19。
3. **没有压测与浸泡载体**：AC-71/71A/71B/72/74 都需要并发提交与长时负载，仓库里只有功能测试。
4. **没有恢复演练载体**：AC-73 要求「删除索引后由原件重建」，删除与重建都需要一个可重复、可计时、可核数的脚本；`POST /documents` 因幂等去重（同 doc_id + 同字节直接返回 `duplicate`）无法用于重建同版本。
5. **AC-75/76/77/78 与本期范围的关系需要逐条落文字**：降级可实跑；供应商核查有技术证据但缺合同文本；Langfuse 本期未部署；抓包未执行。四条都不能靠「默认通过」糊过去。

## 2. 处置

### 2.1 代码

| 文件 | 改动 |
|---|---|
| `app/core/gpu_pool.py` | `queue_position()` 改用独立 `_waiting_lock`；`acquire()` 在**抢主锁之前**自增计数、进闸门即自减，异常退出时归还计数。语义：返回值 = 尚未拿到闸门的线程数 |
| `app/api/reviews.py` | `GET /reviews/{task_id}` 新增 `queue_position` 字段（无显存池时返回 `null`，不伪造 0） |
| `scripts/load_test_qa.py`（新增） | asyncio + httpx，支持 `--concurrency/--total`；记录端到端时延、错误、`queue_position` 时序与吞吐，输出 JSON；明确标注数据库执行窗口「含排队、秒级量化」 |
| `scripts/soak_test.py`（新增） | 定时提交 QA 请求，采样后端 RSS 与句柄数，输出首/末/峰值与变化率 |
| `scripts/rebuild_index.py`（新增） | `--probe` 查 Milvus 条数、`--drop` 删集合、`--rebuild` 由对象存储原件重新解析→清洗→切分→嵌入→写库，逐阶段计时并核数 |
| `tests/test_m5_queue_observability.py`（新增） | 3 条：接口暴露位次、无池时为 `null`、位次计数不被长操作阻塞 |

### 2.3 测量口径修正（重要）

`review_tasks.started_at` 由编排器在任务创建时写入（检索之前），窗口含 GPU 排队；`_now()` 只有秒级精度。
因此数据库执行窗口取出来是整秒值（`exec_p95 = 2.0 s`），**既不是「不含排队」也没有可用分辨率**。
本次不改时间戳格式（避免牵动接口字段与既有解析），改用「并发 1 串行基线 + 客户端实测」作为
AC-71「执行时延（不含排队）」的判据来源，并在压测报告中写明这一替换及其理由。
