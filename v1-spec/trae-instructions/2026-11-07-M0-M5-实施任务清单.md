## 0. 先读这一段（不读会做错方向）

### 0.1 你要建的是什么

一个**内部合规自查工具**：输入一条 GIPS 条款与一家机构的 P&P 手册、台账，输出「具备 / 部分具备 / 缺口 / 证据不足」四态判定，并给出可回验的条款引用。

它**不计算** TWR/MWR，**不出具**合规意见，**不替代**验证。任何输出里出现「已验证」「合规通过」字样都是缺陷。

### 0.2 三条会决定架构的硬约束

**① 只有一台本机 GPU：RTX 4060 Laptop，8 GB 显存，算力 8.9。**
没有云 GPU，一期也不会有。因此：

- 生成模型只能是 8B 级 4bit 量化，上下文上限 4096，**并发只能是 1**。
- 嵌入（bge-m3，约 1.2 GB）、重排（bge-reranker-v2-m3，约 1.2 GB）、生成（约 5 GB）**三者不能同时常驻**，必须分时独占。这不是优化项，是能不能跑起来的前提。
- 任何「三个模型都 load 好常驻内存」的设计一律不可实施，写完就会被 OOM 打回。

**② OCR 全部走云端，本地不装任何 OCR 模型。**
PaddleOCR 常驻约 2 GB，装上就挤掉生成模型的窗口。所以 OCR 的兜底不是「退回本地」，而是「换第二家云供应商重试」。本地跑 OCR 是不可接受的降级路径。

**③ 有文本层的 PDF 不送 OCR。**
现有 GIPS 手册与 P&P 都是原生 PDF，文本层完整。对这类文件跑 OCR，等于把 100% 准确的字符流换成 97% 的识别结果，同时多付一次按页费用、多一次页面图像出域、多一层锚点漂移风险。**OCR 只在文本层不可用时发生。**

### 0.3 现有资产可以直接复用，不要重写

`../../src/` 下已有经过实测的代码，直接接：

| 文件 | 作用 | 复用方式 |
|---|---|---|
| `../../src/extract.py` | 双栏 PDF 提取，按 x0 分栏，噪声过滤 | 作为 `parser/pdf_text.py` 的基础，改造成可配置 |
| `../../src/chunk.py` | 切分，支持 `--mode fine/coarse` | 作为 `parser/chunker.py` 的基础，补条款边界策略 |
| `../../src/eval_retrieval.py` | 检索评测（R@1/5/10、MRR、McNemar） | 作为 `eval/run_eval.py` 的基础，补 golden/dev 分离 |
| `../../src/build_pairs.py` | 双语 pair 对齐（单调 DP） | 已有 69 对、置信度中位 0.805，可直接作为 `bilingual/pairing.py` |

**关键实测结论已固化，不要推翻重做**：
- 跨语言检索不需要翻译，用 bge-m3 单套向量空间即可。中文查询英文索引实测 R@1 0.550 / R@5 0.900，与英文查询差异不显著（McNemar R@5 p=0.625）。
- 中文侧**不单独建索引**，只作显示层。双语 chunk 以 pair 为原子。
- 查询指令前缀无收益（±1 条），不要加。

### 0.4 遇到规格没写的地方

**停下来问，不要自己编。** 尤其是：错误码、字段名、状态机迁移。这些一旦自造，验收时会对不上，返工成本高于问一次。

## 1. 技术栈（已定，不可替换）

| 层 | 选型 | 版本约束 / 注意 |
|---|---|---|
| 语言 | Python 3.11 | 用仓库虚拟环境中的 `python` |
| Web | FastAPI + uvicorn | 单体，不用微服务拆分 |
| 向量库 | Milvus（docker standalone） | 稠密 + BM25 稀疏；**标量过滤必须在候选集之前** |
| 关系库 | SQLite（WAL） | 单写者 + 单写队列；触发器禁 UPDATE/DELETE |
| 缓存 | Redis | 语义缓存；key 含 `index_version` |
| 对象存储 | 本地文件系统 | 原件与快照；不引入 MinIO 也可 |
| 嵌入 | bge-m3（本地） | 已下好在 `../../models/bge-m3` |
| 重排 | bge-reranker-v2-m3（本地） | fp16，与嵌入不同时常驻 |
| 生成 | Qwen3-8B-Instruct 4bit（本地） | **优先 llama.cpp GGUF Q4_K_M**；vLLM+AWQ 作备选 |
| OCR | 阿里云 OCR（主）/ 腾讯云 OCR（兜底） | 云端；适配层归一为 `OcrResult` |
| ASR | 阿里云 ASR | 云端；不装本地 whisper |
| 图片理解 | Qwen-VL | 云端 |
| 观测 | Langfuse（自托管）+ Prometheus | trace 含正文，不得出域 |

### 1.1 生成模型为什么优先 llama.cpp 而不是 vLLM

vLLM 启动时按 `gpu_memory_utilization` 预分配显存，8 GB 卡上留给 KV cache 的余量很小，一旦并发或上下文稍大就 OOM；它的优势是吞吐，而本机并发只有 1，用不上。

llama.cpp 按需分配、可精确控制 `n_ctx` 与 `n_gpu_layers`，8 GB 上更可控、启动更快、OOM 行为可预测。**先按 llama.cpp 实现，接口抽象成 `LLMBackend`，将来换 vLLM 只换实现。**

1. **ACL 过滤必须放在 Milvus 的 search 参数里，不许在返回结果上过滤。** 结果上过滤会导致「召回 20 条，过滤后剩 8 条」，那些被过滤掉的块仍然消耗了召回名额，等于变相降低了召回率。更严重的是，如果过滤逻辑有 bug，越权内容已经进了应用内存。
2. **T-1-09 的 golden 是只读的。** 任何人在调参期间改了 golden，该版本就不能再作为验收对象。这条写进 CI，不靠自觉。

**M2 的三个坑**：

1. **回验器是这套系统唯一不能省的东西。** 4k 上下文迫使模型分段生成，它失去了「一次看全」的全局视野，靠模型自己保证一致性已经不可能。回验器不依赖模型视野，逐锚点独立核验——这是分段的补偿手段，不是可选项。
2. **回验器里出现任何 `import llm` 或 `requests` 都是设计错误。** 它只读原件与数据库。
3. **`NOT_APPLIES` 之后不能再输出任何「顺带提一句」的内容。** 这类提示在人工审查时会变成误判来源：审查员会想「系统说适用性不成立，但提到了缺口，是不是该查一下」。

## 4. 全局禁止事项（违反即返工）

| 禁止 | 原因 |
|---|---|
| 引入 LangChain / LlamaIndex | 隐式重试与 prompt 拼装会让链不可复现；本项目链路必须逐步可记录、可重放 |
| 回验器内调用任何模型或网络 | 回验的价值在于「不依赖模型判断」，一旦调模型即失去意义 |
| 用固定长度带重叠切分 | 同一段内容落进两个 chunk，`span_text` 在两处都能匹配，回验器无法判断哪个是原始锚点 |
| 在检索结果上做 ACL 过滤 | 越权内容已进内存；且被过滤的块消耗了召回名额 |
| 本地部署 OCR / ASR 模型 | 2 GB + 1.5 GB 显存占用会挤掉生成模型，破坏分时独占 |
| 三个模型同时常驻 | 8 GB 装不下，必然 OOM |
| 对 `draft_only` finding 提供任何签署绕过参数 | 绕过参数一旦存在，draft 机制等于没有 |
| 静默截断超上下文的输入 | 证据被截一半而锚点仍指向整段，回验器抓不到这种缺失 |
| 自动拆分超过 50 条的 `scope` | 会让「一次任务」与「一个 finding」的对应关系丢失 |
| 在对外材料/UI 中把 `draft` 结论表述为正式审查结论 | 这是产品定性问题，不是文案问题 |
| 修改 `v1-spec/` 下的四份规格 | 规格变更走变更单，代码适应规格，不是反过来 |
| 调参时使用 `golden-v1.jsonl` | 一旦接触，该模型版本不得再作为验收对象 |

## 5. 每完成一个任务的自检

```powershell
# 1. 起服务
python -m uvicorn app.main:app --reload

# 2. 跑该任务对应的 AC（tests/ 下按 AC 编号组织）
python -m pytest tests/ -k "AC_12A" -v

# 3. 显存必须干净退出（不允许残留进程）
nvidia-smi --query-compute-apps=pid,used_memory --format=csv

# 4. 规格一致性（只在改了接口时跑）
python -c "print('spec 只读，改动须走变更单')"
```

**测试文件命名规范**：`tests/test_ac_<编号>.py`，与验收标准一一对应。这样验收时能直接回答「这条 AC 谁验的、什么时候验的」。

## 7. 最容易被忽略但会影响验收的三件事

1. **T-0-06 的显存基线报告是 M0 的阻断项。** 它不是一个「顺便测一下」的脚本，而是回答「这套方案在这张卡上到底成不成立」的唯一证据。峰值超 7.5 GB 就要重新设计分时策略，不要硬跑。
2. **`labeler_prompt_hash` 必须真存。** AI 标注的可信度全靠「这次标注和上次是不是同一个标注器」这个判断，缺这一项，历史指标全部不可比。
3. **AC-71 是两个时延，不是一个。** 只报执行时延会让评审以为系统吞吐很高，只报端到端时延会让评审以为模型很慢。两个数字都要，且都要说明口径。
