# 规格机检工具

四个脚本随仓库走，换机器不用改路径。

| 文件 | 来源 | 作用 |
|---|---|---|
| `spec_sync.py` | 技能 `spec-propagation/scripts/` | **代码回写门禁**：代码改了要不要回写规格、变更单追溯节三行齐不齐 |
| `spec_gate.py` | 技能 `spec-propagation/scripts/` | **版本门禁** 4 项：改了正文必须升版、PRD 改动必须开单、下游必须跟版 |
| `spec_link.py` | 技能 `spec-propagation/scripts/` | **跨文件联检** 9 项，退出码非 0 即禁止签发 |
| `prd_lint.py` | 技能 `enterprise-rag-prd/scripts/` | PRD 单文件结构细检 11 项 |
| `规格规程模板.md` | 技能 `spec-propagation/references/templates.md` | CHG 变更单、commit message、钩子三个模板 |

配套索引在 `v1-spec/codemap.md`：代码路径 → 规格编号。门禁用它判断"你改的这个文件挂在哪条 R / AC 上"。**新增模块要补一行**，否则新模块的改动等于没有规格归属。

**除模板外四份脚本都是副本，不是主版本。** 主版本在技能目录里（`~/.workbuddy/skills/...`）。技能侧改了校验规则要重新复制，否则这里跑的是旧口径——旧口径最坏的后果不是报错，是静默放过。

## 用法

在**仓库根**执行（不是在本目录）：

```bash
python v1-spec/tools/spec_sync.py --root v1-spec
python v1-spec/tools/spec_gate.py --root v1-spec
python v1-spec/tools/spec_link.py --root v1-spec
python v1-spec/tools/prd_lint.py v1-spec/spec/PRD.md
```

`--root` 指向 `v1-spec`，因为脚本按 `spec/`、`changes/` 两个子目录定位文件，而四件套在 `v1-spec/spec/` 下。

**顺序不能换**：`sync` → `gate` → `link`。前者报根因，后者报后果。

- 只跑 `gate`+`link` 时，"代码改了但规格一个字没动"会一路绿灯 —— 因为四份内部依然自洽。这正是最容易发生、也最该被拦的一种。
- 先跑 `sync` 再跑 `gate`：根因（代码改了没写规格）会先报出来，不至于被"版本没升"这种后果性报错盖住。

## spec_sync 查什么

它只看 **staged 内容**（`git diff --cached`），因为那才是这次真正要提交的东西。无 git 或无 HEAD 时全部跳过。

| # | 检查 | 抓的漏网类型 |
|---|---|---|
| 1 | 相对 HEAD，哪些代码文件被改过 | 判断这次提交是不是动了实现 |
| 2 | 代码有改动 → `changes/` 必须有 CHG，且含 `## 代码变更追溯` 节 | **改了代码懒得改文档**；事后补不出追溯 |
| 3 | 追溯节声明了 R / CT / API / AC 编号 → 四份规格必须真的被改过 | **声明了影响却没回写**，等于自己给自己签免责 |
| 4 | 追溯节列的代码路径必须真实存在于本次 diff | 事后编造改动范围 |

声明「规格影响：无」是允许的（纯重构、加日志、改类型注解）。但若改动文件在 `codemap.md` 里挂着规格编号，会打 WARN 提示复核——这是防止「永远写无」的唯一手段。

实际改动的代码文件未被追溯节覆盖时只 WARN 不 FAIL：测试与配置文件经常是顺带改的，为它们阻断提交会让人习惯性 `--no-verify`，那时门禁就废了。

## spec_gate 查什么

拿工作区与 `HEAD` 比。无 git 或无 HEAD（首次提交）时，前三项降级为 WARN，只保留第 4 项。

| # | 检查 | 抓的漏网类型 |
|---|---|---|
| 1 | 哪几份规格被改过 | 判断改动范围 |
| 2 | 被改过的文件，版本必须大于 HEAD 里的版本 | **改了正文懒得升版**——最常见，也最致命 |
| 3 | PRD 改了就要求 `changes/` 下有新增或修改的 CHG | 改了口径没留变更记录 |
| 4 | 三份 `上游版本` == PRD 当前版本 | 升了 PRD 忘了带下游 |

第 2 项只能比出"没升"，比不出"升得对不对"（v1.1 → v1.9 也算前进）。版本号是否有意义，仍要人看 CHG 里的变更摘要。

## spec_link 查什么

| # | 检查 | 抓的漏网类型 |
|---|---|---|
| 1 | 四份存在 + 版本头字段齐全 | 新建文件忘了加头 |
| 2 | 派生文件「上游版本」== PRD 版本 | 改了 PRD 没同步下游 |
| 3 | ID 双向闭合（定义 ↔ 引用） | 引用了不存在的 AC / API |
| 4 | AC 含 `R-\d`、API 含 `CT-\d` | 条目无上游出处 |
| 5 | 计数断言与实际一致 | 删了正文没改标题和计数 |
| 6 | 四份变更单号一致 + CHG 文件存在 | 改了文件但没开单 |
| 7 | 残留词表 + 占位符（TODO / 待填） | 旧口径回潮、半成品提交 |
| 8 | 契约六块齐备 | 契约只写了字段表 |
| 9 | 验收五节齐备 + 已签发时有未勾项 | 验收退化成断言清单 |

**三道合起来也查不出的**：语义错配（引用写对了编号但指错内容）、编号撞车（两个不同含义的条目用了同一 ID）、代码是否真的实现了那条 AC。这三类只能人看，别指望脚本。

## 六步规程

1. 读四份文件的版本头，`上游版本` 与 PRD 版本不一致 = 链已断，先补同步再做新变更
2. 改代码
3. **判断要不要回写规格**：这次改动会不会让一个本来通过 AC 的实现变成不通过？会就回写
4. 开 `changes/CHG-YYYYMMDD-NN.md`，写 `## 代码变更追溯` 三行，下游影响三份逐条回答
5. 按 `PRD → 契约 → 接口 → 验收标准` 单向改，下游发现上游错了回改上游，不许在下游打补丁
6. 跑三道门禁，任一 FAIL 不为 0 不许说"完成"；四份同 commit

## 为什么必须有钩子

commit 约定靠"每次记得"必然退化，三周后就回到想起来才更新。只有提交被拒是硬反馈。钩子已装在 `.git/hooks/pre-commit`，随仓库提交了脚本本体，但 `.git/hooks/` 本身不入库——**换机器后要重新装一次**：

```bash
cp v1-spec/tools/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```
