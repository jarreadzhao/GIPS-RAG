# GIPS RAG 项目规则

规格是承诺，代码是事实。两者不一致是一种必须消解的缺陷，**没有哪一方默认正确**：
实现中发现规格做不到，就改规格；规格说的行为代码没做，就改代码。
唯一不许的是让两者长期错开、谁也不动。

任何代码改动都必须能追溯到一张变更单，并在单里说清它影响了哪条规格。

## 一、开始任何任务前先读

1. `v1-spec/README.md` — 规格包导航与阅读顺序
2. `v1-spec/trae-instructions/2026-11-07-M0-M5-实施任务清单.md` — 52 个任务与对应 AC
3. `v1-spec/spec/验收标准.md` — 你交付的东西要过哪道门

规格文件在 `v1-spec/spec/`，**不能直接改**。任何一处改动都要走 `changes/CHG-*.md` 变更单，并回答"为什么原来的写法不成立"。

要区分两种"跟着代码改规格"：

- **合法**：代码实现出来才发现规格写漏了、写错了、写宽了 → 如实回写，这是规格在追认真实行为
- **不合法**：代码没做到，就把 AC 改宽让它通过 → 这是把判据改成免责声明

两者的区别不在动作，在**有没有降低标准**。回写完成后，原本不通过的实现应当仍然不通过。

## 二、代码先改、规格后补：回写方向写清楚

派生链单向：**PRD → 契约 → 接口 → 验收标准**。但变更的**发起方**经常是代码。

典型场景：写 `gpu_pool.py` 时发现三个模型没法常驻，只能分时独占。这时 PRD 里多半没这句话，或者写的是别的。三种处置：

| 情形 | 做法 |
|---|---|
| 代码对，规格没写或写错 | **回写 PRD**：补一条 R、改对应章节；再按派生链改契约 → 接口 → 验收 |
| 规格对，代码图省事 | 改代码，不动规格 |
| 两边都不全对 | 以业务事实为准重写那条规格，再让代码对齐 |

**回写的方向永远是 PRD → 契约 → 接口 → 验收，不是反过来。** 即使事实是代码先发生，规格也必须从上往下改一遍，让下游三份能逐层追认。禁止只改验收标准让它迁就代码——那是把判据改成免责声明。

判断"要不要回写"的一句话标准：

> 这次改动，会不会让一个本来通过 AC 的实现变成不通过，或者让一个本来不通过的行为变成通过？
> 会 → 必须回写规格。不会（纯重构、加日志、改类型注解）→ 在 CHG 里写「规格影响：无」并说明。

拿不准就写编号。多写一条规格影响，代价是翻一遍文档；漏写，代价是文档从这天起开始失真。

**回写时按这个顺序做**：

1. `grep -n "R-46" v1-spec/spec/PRD.md` 找到那条需求的原文，读它现在写的是什么，别凭记忆改
2. 分清差异属于哪种：**漏写**（代码做了规格没提）／**写错**（规格说的行为和代码不同）／**写宽**（规格允许了代码没做的）
3. 改正文。要新增 R 条目时，先 `grep -c "| R-" v1-spec/spec/PRD.md` 数一下再取号——编号撞车机检查不出来，两个不同含义的 R-7 会让后续引用全乱
4. 按派生链改契约 → 接口 → 验收，逐层追认
5. 四份齐升版，开 CHG，写 `## 代码变更追溯`

## 三、改了规格就是新版本

四份文件头各有三个字段：`版本` / `上游版本` / `变更单`，缺一不可。

| 情形 | 版本怎么走 |
|---|---|
| 改了 PRD 正文 | PRD `版本` +0.1（v1.1 → v1.2）；契约 / 接口 / 验收的 `上游版本` 跟到 **v1.2**，三份自己的 `版本` 也各 +0.1 |
| 只改了契约正文（PRD 未动） | 契约 `版本` +0.1；`上游版本` 不变；PRD / 接口 / 验收 不动 |
| 只改错别字 | 同样算改动，同样升版。可以并进当次变更，但不能不升 |
| 想回退到旧口径 | **不许把版本号改小**。新开一版，在 CHG 里写「回退自 vX.Y，原因 …」 |

四份的 `变更单` 必须是同一个编号，且 `changes/CHG-*.md` 真实存在。改了 PRD 却没开单，视为未发生变更——钩子会直接拒绝提交。

改任何一份前先读四份的版本头：某份的 `上游版本` 与 PRD `版本` 不符，说明链已断，先补同步再改。规格文件的标题名与编号体系一律照抄，机检靠名字匹配，自创同义词等于让下游失联。

**这条为什么必须机器管**：代码写顺了顺手改一句 PRD，是最高频也最无感的操作。人不会觉得自己在"发新版"，下游三份就这么悄悄过期了。

## 四、每完成一个任务，固定五件事

1. 从任务清单里抄出本任务对应的 **R / CT / API / AC 编号**，写进 CHG。写不出编号，说明这次改动没有规格归属，先停下来确认要做什么
2. 改代码
3. **判断要不要回写规格**：按第二节那句话过一遍；要回写就按 PRD → 契约 → 接口 → 验收 的顺序改全
4. 在 `v1-spec/changes/` 下新建或补写 CHG，「下游影响」逐条回答三份，并写 `## 代码变更追溯` 三行（格式见 `v1-spec/codemap.md` 末尾）
5. 跑三道门禁，FAIL 不为 0 不许说"完成"

```bash
python v1-spec/tools/spec_sync.py --root v1-spec   # 代码改了：规格追认了吗、追溯节三行齐不齐
python v1-spec/tools/spec_gate.py --root v1-spec   # 规格改了：版本有没有前进、有没有开单
python v1-spec/tools/spec_link.py --root v1-spec   # 四份之间：上游版本链、ID 闭合、六块五节
python v1-spec/tools/prd_lint.py v1-spec/spec/PRD.md
```

三步顺序不能换：`spec_sync` 报根因（代码改了、规格没跟），`spec_gate` 报后果（没升版、没开单），`spec_link` 报细节（四份对不上）。反过来的话，只改 PRD 不升版会一路绿灯——四份内部依然自洽。

`v1-spec/codemap.md` 是代码到规格的索引：改哪个文件该翻哪几条 R / AC，查它。新增模块要补一行，否则新模块的改动等于没有规格归属。

commit message 格式：`spec(CHG-20261109-01): 一句话标题`（纯代码改动可用 `feat(T-0-03): ...`，但涉及规格同步时必须用 spec 前缀）。

仓库已装 pre-commit 钩子，串联 `spec_sync` → `spec_gate` → `spec_link` 三道，任一不过即拒绝提交。**不要用 `--no-verify` 绕过**，除非在 message 里写明理由。

## 五、硬禁令（违反即为缺陷，不是风格问题）

| # | 禁令 | 依据 |
|---|---|---|
| 1 | 禁止在检索结果上做 ACL 过滤。过滤必须在向量检索的标量条件下推，放到重排之后等于没做 | R-18、AC-15 |
| 2 | 禁止嵌入/重排/生成三个模型常驻显存。8 GB 卡必须分时独占，由编排器单点负责卸载 | R-46、AC-12A |
| 3 | 禁止对有文本层的 PDF 调 OCR。只有文本层字符数 < 50 且页面非空白才走云 OCR | R-47、AC-12C |
| 4 | 禁止为 `draft_only` 的 finding 提供任何 force / override / 强制签署参数 | R-48、AC-12D |
| 5 | 禁止让模型自证引用正确。锚点校验必须由不依赖模型的规则引擎做字节级回验 | R-30、R-34 |
| 6 | 禁止 `task_type=formal` 与 `supply=managed` 组合下发到生成服务，编排器侧就要返回 422 | R-3、AC-57 |
| 7 | 禁止 C 类台账进入向量库、prompt 或任何外部调用 | R-10、AC-11 |
| 8 | 禁止在模型输出里出现实数。金额与比率只允许 `calc://{calc_id}` 占位符 | R-32 |

## 六、环境

- Python：仓库虚拟环境中的 `python`（已加入 PATH）
- 模型权重在 `models/`（不入库）；运行产物在 `var/`（不入库）；密钥在 `.env`（不入库）
- 硬件边界：RTX 4060 Laptop 8 GB，生成模型只能 4bit、上下文 ≤ 4k、并发 1
- 生成推理用 llama.cpp GGUF，不用 vLLM（vLLM 按比例预分配显存，8 GB 上 KV cache 余量不足）

## 七、报告口径

- 任何性能/质量数字必须给出测量条件（数据集、模型版本、硬件）。没有条件的数字不写进报告
- 未实测的按「设计目标值」标注，不许写成已达成的结果
- 失败与缺陷照实记录，包括「已知未修」。报告里没有缺陷，评审时就会被当成隐瞒
