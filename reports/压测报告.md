## 1. 并发压测（AC-71 / AC-71A / AC-71B）

### 1.1 两个时延怎么取

本机推理并发为 1（`GPUPool.acquire()` 全程持有同一把锁），20 路并发下用户感知的等待
主要来自排队。为了不把「吞吐能力」和「单任务性能」混成一个数字，分两次测：

| 口径 | 取法 | 回答的问题 |
|---|---|---|
| 端到端时延（含排队） | 客户端实测 `submit → response` | 20 路并发下用户要等多久 |
| 执行时延（不含排队） | 并发 1 串行基线，客户端实测 | 单个任务本身跑多快 |

**为什么不用数据库里的 `started_at → finished_at`**：`review_tasks.started_at` 由编排器在
任务创建时写入（检索之前），窗口里包含 GPU 排队；且 `_now()` 只有秒级精度，取出来是整秒值
（实测 `exec_p95 = 2.0 s` 即由此而来）。这个窗口既不是「不含排队」，也没有可用分辨率，
**不能作为 AC-71 的判据**，只作为「服务端确实执行完」的辅助证据。

### 1.2 20 路并发（`scripts/load_test_qa.py --concurrency 20 --total 20`）

| 指标 | 实测 |
|---|---|
| 提交总数 / 并发 | 20 / 20 |
| 错误数、错误率 | 0 / 0.0 |
| 总墙钟 | 2.816 s |
| 端到端 P50 / P95 | 2.093 s / 2.725 s |
| `queue_position` 采样峰值 | 19（14 次采样，0.1 s 间隔） |
| 队列随进度变化 | 0 → 16 → **19** → 19 → 18 → 19 → 15 → 8 → 2 → 0（峰值后单调收敛） |
| 服务端并发（推定） | `峰值 19 + 1`，与「并发恒为 1 + 19 个等待」一致 |
| 数据库执行窗口 P95 | 2.0 s（整秒量化、含排队，**不作判据**） |
| 吞吐（短时推算） | 25 566 任务/小时（按 20 / 2.816 s 折算，样本 20，仅供量级参考） |

### 1.3 串行基线（`--concurrency 1 --total 20`）

| 指标 | 实测 |
|---|---|
| 错误数、错误率 | 0 / 0.0 |
| 总墙钟 | 5.87 s |
| 执行时延 P50 / P95 | **0.270 s / 0.420 s** |
| `queue_position` | 恒为 0（无排队，符合预期） |

### 1.4 判定

| AC | 判据 | 实测 | 判定 |
|---|---|---|---|
| AC-71 | 执行时延（不含排队）P95 ≤ 12 s；错误率 ≤ 0.01；服务端并发恒为 1，无 OOM | 执行 P95 = **0.42 s**；错误率 0；`queue_position` 峰值 19 且并发推定 1；无 OOM | **通过** |
| AC-71A | 队列等待 P95 ≤ 15 分钟；`queue_position` 随进度递减且与实测一致 | 端到端 P95 2.73 s（远低于 900 s）；采样序列 19 → 15 → 2 → 0，与端到端–执行差值（≈2.3 s）方向一致 | **通过** |
| AC-71B | 单机吞吐 ≥ 30 任务/小时 | 25 566/h（20 并发短批折算）；串行 12 269/h | **通过（样本量小，见 1.5）** |

### 1.5 局限（不得忽略）

1. **样本量**：每轮 20 个任务，`P95` 实际落在第 19 个观测上，只能说明量级，不能替代长时统计。
2. **无生成模型**：接入 GGUF 生成后，每个任务要清空 embed/rerank 槽位再加载生成模型（8 GB 分时独占），
   单任务执行时延会从亚秒级跳到数十秒级。届时 12 s 阈值需按 PRD 1.3 的目标值重新核对，
   本报告数字**不能**外推为「带生成的问答 P95」。
3. **吞吐不宜外推**：25 566/h 是 20 个抽取式任务的短批折算，瓶颈在 CPU 侧重排与回验，
   不代表生产负载下的处理能力。

## 4. 降级演练（AC-75）

- 方式：`GIPS_EGRESS_ENABLED=false` 重启服务（云通道关闭）
- 降级耗时：杀进程 → `healthz` 恢复 **3.23 s**（远低于 30 分钟）

| 检查项 | 实测 |
|---|---|
| `GET /documents/gips2020` | 200，0.02 s |
| `POST /retrieval/test` | 200，命中 5 个条款，29.85 s（**冷启动加载嵌入模型**，非降级导致） |
| `POST /reviews`（qa） | 202 / `succeeded`，0.26 s |
| `POST /documents`（无文本层，必须 OCR） | **202 受理**，`task_id=tsk_…`、`queue_position=0`；任务终态 `failed`、`business_code=ocr_failed`；文档 `status=failed` |
| 出域台账 | `egress_logs` 新增 1 行：`state=failed`、`dlp_verdict=egress_disabled`、`byte_size=15630`，无载荷出域 |

**判定：通过。** 只读/查询接口可用、降级在 30 分钟内完成；AC-75 原文「写请求进入排队」由
CHG-20261110-11 补齐后满足——云通道关闭时上传仍返回 `202` 与任务号，解析/切分/建索引由写队列
推进，失败以任务终态 `failed` + `business_code=ocr_failed` 呈现，不再同步 504 丢单。
任务载体复用 `review_tasks`（`task_type=ingest`），查询走 `GET /reviews/{task_id}`。
演练用的 `drill-egress-off` 台账行已清理，`documents` 仍只有 `gips2020` 与 `gips2020-zh`。

复现要点（无脚本，三步）：

1. `$env:GIPS_EGRESS_ENABLED = "false"` 后按 `docs/运维手册.md` 1.2 节重启后端（演练可另起端口与临时库，避免污染交付库）；
2. 依次请求 `GET /documents/gips2020`、`POST /retrieval/test`、`POST /reviews`（qa）；
3. 用任一**无文本层** PDF 调 `POST /documents`（`doc_id` 自拟，如 `drill-egress-off`），
   期望 **202** 与 `task_id`；轮询 `GET /reviews/{task_id}` 到终态，应见 `status=failed`、
   `business_code=ocr_failed`，`document.status=failed`；查 `SELECT * FROM egress_logs ORDER BY rowid DESC LIMIT 1`
   应见 `dlp_verdict=egress_disabled`、`byte_size` 非 0 但无载荷出域；演练后删掉该 `doc_id` 的台账行。
