**Recall@5 = 1.0 的正确读法**：编号变体占一半查询，结构化通道可直接命中；义务首句变体是从原文截出的连续子串，稠密检索近乎必中。这个数字说明「查询与原文足够像时能召回」，**不说明检索能力强**。有信息量的是 Recall@1 = 0.8194 与 MRR = 0.8946——约 18% 的条目首位不是目标条款，集中在同章近义条款之间。

**为什么不再是 N/A**：`eval/golden/golden-v1.jsonl` 与 `eval/dev/dev-v1.jsonl` 已按 `app/eval/dataset.py` 的目录隔离要求冻结，gold 由生成器（`scripts/gen_selfeval.py`）直接给出，不经过模型也不经过人工，因此不需要 AI 初标与抽检即可计算召回。原先 N/A 的依据是「无真实工单问题池」，该缺口未变，只是本期不再用它作判据。

结论：**AC-13、AC-14 在本期口径下通过；AC-24D 因口径移出不适用。** 剩余观测缺口见第 4 节与 `reports/自生成口径评测.md` 第 7 节。

## 5. 计数口径核查（Milvus 986 vs 793）

测试条件：容器以 `docker compose up -d` 起至 milvus `healthy`，`pymilvus.MilvusClient("http://127.0.0.1:19530")`，集合 `gips_chunks`。核查日期 2026-11-10。

| 口径 | 结果 | 说明 |
|---|---|---|
| `get_collection_stats()` → `row_count` | **986** | 含已软删除、尚未 compact 的实体 |
| `query(filter="", output_fields=["count(*)"])` | **793** | 不含软删除实体 |
| `query(filter='index_version == "idx_58bd974484e82424"')` | 793 | 与 `gips2020` 的 chunk 数一致 |
| `query(filter='doc_id == "gips2020"')` | 793 | SQLite `chunks` 中 `gips2020` 也是 793 条 |
| `query(filter='doc_id == "gips2020-appendix-sample"')` | **0** | SQLite 中该文档有 4 条 chunk |
| `query(filter='index_version == "idx_sample_v1"')` | **0** | `documents` 里该文档回显的索引版本 |

结论：

1. **986 − 793 = 193 是软删除未压缩的实体**，不是重复写入，也不是两个索引版本相加。生产代码用的是带 `index_version` 过滤的 `count(*)`（`app/index/builder.py` 的 `count()`），口径正确，AC-10 的计数比对不受影响。**不要把 `get_collection_stats()` 用于健康检查或对账**——它会把已删实体算进去，导致「Milvus 比 SQLite 多」的假告警。
2. 反过来，`gips2020-appendix-sample` 是真问题：`index_status=active` 而向量数为 0，等于把「没建好索引」标成了「可用」，即 `DEF-M1-02`。该文档是 2026-11-09 走查用的附录样例，4 条 chunk 与 2 页页文本（p103、p104）经旁路写入，未走 builder 的条数核对。
3. 顺带确认一项正向事实：`gips2020` 的 `COUNT(DISTINCT provision_id)` = **485**，与 `reports/条款证据清单.csv` 的 485 行一致，可作 AC-81 分母的旁证。
