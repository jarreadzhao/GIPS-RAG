## 1. 查询集构造方法

| 项 | 内容 |
|---|---|
| 来源 | `reports/条款证据清单.csv` 的 485 条带编号条款 |
| 抽样 | 等距抽 200 条（`round(i*(n-1)/(200-1))`），保证 8 个章都有代表，结果可复算、不依赖随机种子 |
| 变体 | 偶数条按**条款编号**查（100 条），奇数条按**义务首句**查（100 条）；义务首句取 `要求摘要（原文）` 到第一个句号为止 |
| gold | 该条款自身的 `provision_id`，由构造过程给出，不经过模型、不需要人工标注 |
| 拆分 | `sha256(item_id)[0] % 5 == 0` 进 dev，其余进 golden → **golden 155 条 / dev 45 条** |
| 冻结 | `eval/golden/meta.json` 的 `frozen_at = 2026-11-10T02:32:54Z`；golden 内容哈希 `sha256:e478b7cf…` |
| 生成器 | `scripts/gen_selfeval.py`，其文件哈希写入每条记录的 `labeler_prompt_hash`（`sha256:39c7adf5…`） |
| 目录隔离 | `eval/golden/` 与 `eval/dev/` 两个目录，由 `app/eval/dataset.py` 强制，同目录混放会被 `load_set` 直接拒绝 |

**关于 AC-82 括号里的「标题」变体**：GIPS 条款没有独立标题，`条款证据清单.csv` 里能当标题用的只有章名，而全库只有 8 个章。用章名查询时 gold 只能是整章 20～85 条，Recall@5 会退化成「章级命中」，与条款级指标不同粒度，不能放进同一个分母。故条款级评测只保留编号与义务首句两种变体，章名查询单列为补充观测（见第 4 节），不参与 AC-82 判定。该口径偏离已由 **CHG-20261110-12** 修订 PRD 1.3、AC-82 与 M1 进入条件，`GAP-M1-02` 关闭；阈值 0.92、两次差值 ≤1pp、200 条总量均未改。

## 5. 这个 1.0 该怎么读

**Recall@5 = 1.0 不是「检索很强」的证据，主要说明查询太像原文。**

1. 编号变体的 100 条查询本身就是 `1.A.1` 这样的字符串，结构化通道（白名单 SQL）能直接命中元数据，等于半开卷。
2. 义务首句变体的 100 条查询是从条款原文里截出来的连续子串，稠密检索对逐字复现的文本几乎必中。
3. 真正有信息量的是 **Recall@1 = 0.8194 与 MRR = 0.8946**：即便查询与原文高度重合，仍有约 18% 的条目第一条不是目标条款，说明重排在同章近义条款之间会选错。这是后续调优的着力点，而 Recall@5 已经封顶，测不出改进。
4. 真实工单口径（用户口语化提问、跨条款复合问题、中文提问）没有覆盖，本期也无法覆盖——没有工单来源。**任何对外表述不得把这个 1.0 说成「检索准确率 100%」。**
