# 索引恢复演练（AC-73）

- 执行日期：2026-11-10
- 判据：`v1-spec/spec/验收标准.md` AC-73 —— 删除 Milvus 索引后**由原件重建**，重建后 Recall@5 达 M1 基线，耗时 ≤ 4 小时
- 结论：**通过**。重建耗时 382.13 s（≈ 6.4 分钟），重建后 Recall@5 = 1.0000，与基线一致

---

## 1. 演练对象与前提

| 项 | 值 |
|---|---|
| 文档 | `gips2020` v1（GIPS 2020 Firms 手册） |
| 原件 | `var/objects/blobs/9c/9c45d87dfc8b653e22839fac8cb0db6f29e402ecb10a4c65ce30e461231d5532.pdf`（811 720 B / 146 页） |
| 原件哈希 | `9c45d87dfc8b653e22839fac8cb0db6f29e402ecb10a4c65ce30e461231d5532`（sha256，与 `documents.file_hash` 一致） |
| 索引版本 | `idx_58bd974484e82424` |
| Milvus | standalone，`127.0.0.1:19530`，集合 `gips_chunks` |
| 清洗/切分 | `.env` 的 `GIPS_CLEANER_VERSION=cleaner-v1`、`GIPS_CHUNKER_STRATEGY=provision`、`chunker_overlap=0` |

这次演练**不碰 SQLite 台账、不碰对象存储**，只删向量库——模拟「Milvus 数据盘损坏/误删集合」这一类最常见的恢复场景。
原件仍在，所以是「由原件重建」，不是「由已有的 chunk 文本重灌向量」。

## 2. 演练步骤与时间线

| # | 动作 | 结果 |
|---|---|---|
| 1 | 重建前探针 `rebuild_index.py --probe` | 集合存在；`row_count_total=793`、`doc_id=gips2020` 793、`index_version=idx_58bd…` 793 |
| 2 | 重建前评测 `run_selfeval.py` | R@1 0.8194 / R@5 1.0000 / R@10 1.0000 / MRR 0.8946 |
| 3 | 删除集合 `rebuild_index.py --drop` | `dropped=true`；集合列表变空 |
| 4 | 复测探针 | `collection_exists=false`，向量库确认丢失 |
| 5 | 重建 `rebuild_index.py --rebuild` | 见第 3 节分阶段耗时；`state=active`，793/793 |
| 6 | 重启服务 | `healthz` 3.23 s 恢复；首次查询触发模型冷加载约 28 s（`retrieval_warmup_timeout_s=120` 豁免） |
| 7 | 重建后评测 `run_selfeval.py` | R@1 0.8194 / R@5 1.0000 / R@10 1.0000 / MRR 0.8946 |

## 3. 重建耗时（RTO 依据）

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 解析（PDF → 页文本 + 块） | 0.725 s | 146 页有文本层，全程未调用 OCR |
| 清洗 + 切分 | 0.174 s | `cleaner-v1` + `provision` 策略，产出 793 块 |
| 嵌入 + 写 Milvus + 条数核对 + 抽样回查 + 切 active | **381.231 s** | 8 条一批编码；瓶颈是嵌入 |
| **重建合计** | **382.130 s** | ≈ 6.4 分钟 |

**RTO 估算**（从「已确认需要重建」起算）：

| 组成 | 耗时 |
|---|---|
| 重建 | 382.1 s |
| 服务重启到可服务 | 3.2 s |
| 首个查询冷启动（模型加载） | ≈ 28 s |
| **合计** | **≈ 6.9 分钟**，远低于 4 小时判据 |

人工发现与决策时间不在上表内。当前系统**不会自动发现**向量库丢失（见第 5 节 OBS-01），
所以真实 RTO 要加上「人工发现」这一段，这一段本期没有可测数据，不写数字。

评测集：`eval/golden/golden-v1.jsonl`，155 条，内容哈希 `sha256:e478b7cf…`，
`X-Role: admin`、`X-Dept: compliance`、`top_k=20`、通道 `dense+sparse+sql`、重排开启。

> 这个数字说明「重建没丢东西」，不说明检索能力强。有信息量的是 R@1 = 0.8194 与 MRR = 0.8946 的重合。

## 5. 演练中发现的问题

| 编号 | 问题 | 证据 | 处置 |
|---|---|---|---|
| OBS-01 | **索引丢失不可自动感知**：集合删除后 `documents.index_status` 仍为 `active`，`GET /documents/{doc_id}` 仍回 `active` | 步骤 4 探针显示集合不存在，而台账仍是 active | 本期如实记录；建议二期加对账探针（SQLite 计数 vs Milvus `count(*)` 定时比对，不一致告警） |
| OBS-02 | 检索返回的 `index_version` 查询串仍含 `idx_sample_v1` | SQLite 中 `gips2020-appendix-sample` 4 条 chunk 仍 `active`（历史走查数据，按 `reports/Q0-引用回链与越界审计.md` 第 7 节保留作 finding 证据） | Milvus 无对应向量，召回不受影响；版本串会误导排障，已记入压测报告 OBS-M5-02 |
| OBS-03 | 重建依赖 `scripts/rebuild_index.py` 内联的入库流水线，与 `app/api/documents.py` 的流水线是两份代码 | 见脚本注释 | 两份当前参数一致（清洗/切分/质量闸门/ACL 打标）；改切分或清洗配置时必须同步，重建后要复核 `index_version` 是否与预期一致 |

## 6. 复现命令

```bash
# 1) 重建前基线
python scripts/rebuild_index.py --probe --index-version idx_58bd974484e82424
python scripts/run_selfeval.py --out var/reports/selfeval_pre_rebuild.json
# 2) 模拟索引丢失
python scripts/rebuild_index.py --drop
python scripts/rebuild_index.py --probe            # 期望 collection_exists=false
# 3) 由原件重建（逐阶段计时写入 JSON）
python scripts/rebuild_index.py --rebuild --out var/reports/rebuild_drill.json
# 4) 重启服务后复测
python scripts/run_selfeval.py --out var/reports/selfeval_post_rebuild.json
```

机器可读结果：`var/reports/rebuild_drill.json`、`var/reports/selfeval_pre_rebuild.json`、
`var/reports/selfeval_post_rebuild.json`。
