## 3. 指标定义

| 指标 | 定义 |
|---|---|
| 页内规范字符流 | 由解析器按阅读顺序把块拼接而成（块间一个 `\n`），偏移随拼接累积。双栏页先按栏排序，所以左栏文字不会被右栏打断 |
| 锚点可回链率 | `chunk.text.strip()` 是页内规范字符流子串的 chunk 数 / chunk 总数 |
| 精确 span 一致率 | `page_text[char_start:char_end] == chunk.text` 的 chunk 数 / chunk 总数（严格相等，不做空白归一化） |
| 重叠违规 | 同页相邻 chunk 的 `[char_start, char_end)` 区间相交的对数 |
| 超长违规 | 字符数 > 1100 的 chunk 数 |
| 跨页违规 | 恒为 0：切分按页分组，结构上不可能跨页 |
| 空块 | `strip()` 后为空的 chunk 数 |

## 4. 关键发现

1. **四策略锚点全部 100%**。修复前的 0.77（EN provision）/ 0.52（ZH）来自偏移基准错误，不是切分算法本身：原实现拿 PyMuPDF 的 `get_text('text')` 原始流做基准，该流按 y 坐标排序，双栏页上块序（按栏）与字符流序不一致，chunk 的 `[min, max]` 区间必然横跨到另一栏。
2. **修复方式**（缺陷 D-1，已关闭）：`pdf_text.extract()` 改为按块累积偏移，双栏先按栏排序再拼流；`cleaner.clean()` 删块后重建字符流并重算偏移；`chunker._emit()` 的分隔符由偏移间隙决定（相邻块 gap=1 用 `\n`，同块内切句 gap=0 不加），顺带修掉 D-5。
3. **端到端复核**：重建索引后 793 条 chunk 全部通过 `page_text[char_start:char_end] == text` 校验（全量，非抽样），不一致 0 条。
4. **`provision` 仍是首选策略**：它是唯一带稳定条款边界的策略（编号覆盖 95.2% / 96.3%），M1 默认继续使用。
5. **`provision_id` 覆盖率**：EN 755/793、ZH 631/655。其余是封面、目录与序言，本来没有条款编号；章/节标题块已归到其下第一条条款。条款正文块覆盖率 100%。
6. **超长块是已知例外**：EN 三种块策略各有 12 条 >1100（最长 1910），均为单个超长段落。遵守「不在段落内切分」的不变量，不强行截断，记录不视为缺陷。
7. **ZH 最短 5 字符**：尾块合并只在「同页 + 同条款」时生效，示例/表格碎片会保留为独立 chunk。非空、不违反边界约束，但属于低信息量块，M1 建索引时应过滤或降权。
8. **`semantic` 仍不建议作默认**：它靠标点断句，会把一个条款拆到多个 chunk，损失条款完整性；锚点问题已修复，但召回粒度不如 provision。

## 5. 结论与对 M1 的影响

- M0/M1 默认 `provision`；四策略数据留档，供 M1 复跑对比（AC-23 的 `config_echo` 需要两套切分配置）。
- D-1（双栏交错）与 D-5（semantic 合成换行）均已修复并有回归测试 `tests/test_anchor_roundtrip.py`，M2 回验器的前置条件已满足。
- 索引已按修复后的切分器重建：793 条、793 条 `active`，`index_version=idx_58bd974484e82424`（绑定 `cleaner-v2` / `chunker-v2`）。
- 遗留：表格结构仍未重建（D-2），`table_cell` 策略无产物，M1 结构化通道只能覆盖台账类表，不覆盖 PDF 内表格。
