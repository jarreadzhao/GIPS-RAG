# 标注规范

- 适用阶段：M0 编写，M1 执行（评测集 v1）
- 上游依据：PRD v1.1 第 1.3、4.11 节；验收标准 v1.1 AC-24、AC-24A～AC-24D
- 使用对象：评测集标注执行人、人工抽检审查员、发布判据审核人
- 核心口径：AI 初标 + 人工分层抽检；**不再使用 Cohen's kappa**
- 状态说明：本文中的门槛多为**设计目标值**，按 PRD 1.3 的约定，全部设计目标值在 M2 首轮盲评后重新标定并升版

## 1. 标注对象与粒度

### 1.1 两层对象

| 层级 | 对象 | 说明 | 存放位置 |
|---|---|---|---|
| 问题级 | 一条审查问题（query item） | 从真实审查工单、未命中池、争议单中抽样得到，200 条，覆盖 A–E 五类场景与中英双语 | `eval/queries-v1.jsonl` 骨架（`gold` 为空） |
| 条款级 | 该问题对应的正确条款集合（gold） | 元素为 `provision_id`，不是 chunk，也不是段落 | 同一 JSONL 的 `gold` 字段 |

`provision_id` 的格式以库表为准，形如 `1.A.4`（见 `db/schema.sql` 中 `provisions.provision_id` 注释）；实际编号以 `docs/条款树-v1.md` 为唯一依据。

### 1.2 只标条款，不标以下内容

- **不标 chunk_id。** 评测算的是「正确条款是否落在前 5」，chunk 是检索实现细节；标到 chunk 会让 golden 绑定某一种切分配置，换切分即失效。
- **不标判定结论。** 标注只回答「这个问题应该由哪条条款回答」，不回答「被审查机构是否满足该条款」。四态判定属于运行时结论，仍须人工盲评，不在评测集标注范围内。
- **不标证据页内的具体句子。** 依据原文只作为标注理由留痕，不作为评测匹配对象。

### 1.3 一条问题的完整标注物

一条问题进入冻结集前，至少具备：问题文本、语言（中/英）、场景类别（A–E）、`gold` 条款集合、标注依据原文、标注器元数据、自一致结果、人工抽检结果。字段级定义见第 3 节。

## 2. 标注流程

PRD 4.11.1 规定五步，顺序不可调换：

| 步 | 动作 | 产物 | 责任人 |
|---|---|---|---|
| 1 取证 | 从真实审查工单、未命中池、争议单里抽样 200 条，覆盖 A–E 五类场景与中英双语 | `eval/queries-v1.jsonl` 骨架，`gold` 为空 | 评测集负责人 |
| 2 初标 | 标注器对每条问题输出候选条款 ID + 依据原文 + 置信度 | `gold` 候选、`labeler_confidence` | 标注器（LLM） |
| 3 自一致 | 同一问题独立标 3 次（temperature 固定），三取二 | 自一致率、分歧项清单 | 标注器 + 流水线 |
| 4 抽检 | 分层抽样 ≥ 20% 且 ≥ 40 条（覆盖全部 5 类场景、覆盖全部低置信项）由审查员判定 | 抽检准确率、错误项 | 人工审查员 |
| 5 冻结 | 通过后打 `frozen_at` 与内容哈希，此后改动须走变更单 | 冻结版评测集 | 评测集负责人 |

### 2.1 AI 初标（步 2）

- 每条问题独立调用标注器。输入只含问题与条款语料，不把检索结果、rerank 分数或候选 chunk 排序作为提示（本规范约定，用于落实 PRD 4.11.2 的防自欺意图）；目的是避免标注器「照着检索器的口味出题」。
- 输出必须包含：候选 `provision_id` 列表、依据原文（可回链到文档与页码）、置信度。
- 标注器必须记录 `labeler_model` 与 `labeler_prompt_hash`；两者任一变化，视同**评测集换版**，历史指标不可直接比较（PRD 4.11.2 第 2 条、PRD 1.3 第 ③ 条）。

### 2.2 自一致（步 3）

- 同一问题以**固定 temperature** 独立标 3 次，不共享上下文、不携带前一次输出。
- 采用「三取二」确定 `gold`：三次结果中至少两次相同的条款集合即为 `gold`。
- 三次结果两两不同（无多数）时，该条 `self_consistency=0`，进入分歧项清单，必须由人工判定后才能进入抽检与冻结。
- 自一致率的整批计算见第 7 节。

### 2.3 人工抽检（步 4）

- 抽检样本不是随机 20%，而是：**全部低置信项 + 全部表格类条款 + 随机补齐到 20%**，且总量 ≥ 40 条、覆盖全部 5 类场景（PRD 4.11.1 步 4、4.11.2 第 3 条）。
- 审查员只看到问题与 AI 给出的 `gold` 候选，不看检索结果与模型指标（本规范约定），独立判定「该 gold 是否正确」。
- 判定结果写回 `human_checked=true` 与人工结论；错误项须记录错误类型。抽检规则与准确率计算见第 6、8 节。

### 2.4 退回重标（任一闸门不通过）

PRD 4.11.1 设三道闸门，**任一不过即整批退回重标**：

| 闸门 | 阈值 | 不通过的含义 | 处理动作 |
|---|---|---|---|
| 自一致率 | ≥ 0.90 | 标注器不稳定，`gold` 不可信 | 先修标注器（模型或 prompt），再整批重标 |
| 抽检准确率 | ≥ 0.95 | 标注存在系统性偏差 | 整批退回重标 |
| 低置信项占比 | ≤ 0.15 | 语料或问题本身有歧义 | 回到步 1 重抽问题（不是只重标） |

补充约定：

- 退回重标必须**换新的 `labeler_run_id`**；不得在旧结果上局部修补后复用同一批次号。
- 未通过闸门的批次不得打 `frozen_at`，不得进入发布判据。
- 冻结后如需改动，一律走变更单，并重新计算 `content_hash`；已接触过 golden 的模型版本不得作为验收对象（AC-24C）。

### 2.5 冻结（步 5）

- 冻结时写入 `frozen_at` 与非空 `content_hash`；`frozen_at` 非空即只读（`db/schema.sql` 中 `eval_sets` 注释）。
- `eval/golden-v1.jsonl`（验收用，只读）与 `eval/dev-v1.jsonl`（调参用，可改）是两个文件、两个哈希。CI 只允许对 golden 跑发布判据，对 dev 跑开发期指标（PRD 4.11.2 第 1 条）。

## 3. 标注字段说明

### 3.1 集级字段：`eval_sets`（以 `db/schema.sql` 为准）

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `set_id` | TEXT | 评测集标识，如 `golden-v1` / `dev-v1` | 与 `version` 组成主键 |
| `version` | TEXT | 评测集版本 | 与 `set_id` 组成主键 |
| `item_count` | INTEGER | 条目数 | 评测集 v1 为 200 |
| `content_hash` | TEXT | 内容哈希 | 冻结时必须与文件实算值一致 |
| `frozen_at` | TEXT | 冻结时间 | 非空即只读；未冻结不得用于发布判据 |

### 3.2 结果级字段：`eval_results`（以 `db/schema.sql` 为准）

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `run_id` | TEXT | 评测运行标识 | 主键 |
| `set_id` | TEXT | 引用的评测集 | 应指向已冻结版本 |
| `metric` | TEXT | 指标名 | 指标名的登记口径由评测流水线固化，本规范只约束值的算法 |
| `value` | TEXT | 指标值 | **定点数字符串**，如 `0.905`，不存浮点近似 |
| `model_version` | TEXT | 被评测的模型版本 | 用于判断是否接触过 golden |
| `config_hash` | TEXT | 配置哈希（切分版本 + 嵌入版本 + 重排开关 + prompt 版本） | **缺配置的结果不得作为发布依据**（契约 CT-10、接口 API-30） |
| `created_at` | TEXT | 创建时间 | — |

### 3.3 条目级字段：gold JSONL 每一行

PRD 4.11.2 明确要求「每条 `gold`」保存以下字段，因此这些字段属于**条目级**，不在 `eval_sets` 表内：

| 字段 | 含义 | 取值/说明 |
|---|---|---|
| `gold` | 正确条款集合 | `provision_id` 数组；三取二的结果 |
| `labeler_model` | 标注器模型标识 | AC-24 强制项，缺失即拒绝发布判据 |
| `labeler_prompt_hash` | 标注器提示词哈希 | AC-24 强制项，缺失即拒绝发布判据 |
| `labeler_run_id` | 标注批次标识 | 换批次不得复用 |
| `labeler_confidence` | AI 初标置信度 | PRD 4.11.1 的字段名；4.11.2 简写为 `confidence`，落地统一用 `labeler_confidence` |
| `self_consistency` | 该条三次标注是否多数一致 | `1` / `0`，算法见第 7 节 |
| `human_checked` | 是否已被人工抽检 | `true` / `false` |

审查落地时另需记录（本规范约定，非 PRD 既有指标）：`human_label`（人工判定结果）、`checked_by`（审查员）、`checked_at`（判定时间）、`error_reason`（错误类型）。这些字段用于生成「错误项清单」，不参与指标定义。

### 3.4 字段与 schema 的对齐说明（待核实）

当前 `db/schema.sql` 的 `eval_sets` 只有 `set_id / version / item_count / content_hash / frozen_at` 五列，**没有** `labeler_model` / `labeler_prompt_hash` 列。按 PRD 4.11.2，这两项是条目级元数据，存放在 gold JSONL 的每一行。

由此产生一个待核实项：AC-24 要求「使用缺 `labeler_model` / `labeler_prompt_hash` 记录的评测集发起发布判据时拒绝」，但库内 `eval_sets` 无可校验列。M1 实现前须确认校验入口——是读取条目级 JSONL 的聚合值，还是在 set 级补存元数据；**在确认前不得假定库内已有该字段**。

## 4. 标注规则

### 4.1 gold 判定标准

一条条款进入 `gold`，须同时满足：

1. **直接约束**：该条款直接规定问题所问的事项，而不是仅出现相同术语。
2. **现行有效**：使用问题所对应的版本（GIPS 2020）与生效期；旧版同编号条款不得作为 gold。
3. **可回答**：仅凭该条款原文即可回答问题，无需再外推。
4. **无遗漏**：若问题同时涉及多条义务（如披露要求 + 计算口径），须全部标出；漏标与错标同样计错。

### 4.2 多条款并列

- `gold` 是**集合**，允许一条问题对应多条条款。
- 集合内不排序、不设主次；评测只看「正确条款是否落在前 5」，不区分 gold 内部的先后。
- 若两条条款内容重复（修订沿革导致），只标现行版本的一条，并在依据原文中注明另一条为历史版本。

### 4.3 表格类条款

- 本规范以条款树中对应 `chunk_type='table_cell'` 的条款为「表格类条款」（PRD 只写「全部表格类条款」，未给识别口径，此处按 schema 的 chunk 类型落地）。
- 标注仍落到 `provision_id`；不得因为内容在表格中就改标 cell 或跳过。
- 表格类条款**全部进入抽检**，不参与随机抽样（PRD 4.11.2 第 3 条）。

### 4.4 低置信项

- 低置信项**全部进入抽检**。
- 低置信不等于「无 gold」：不得因为置信度低就留空或删条；必须由人工判定后写入结论。
- 低置信的具体数值阈值 PRD 未给出，见第 11 节待核实项。

### 4.5 中英双语

- 同一问题在冻结时必须绑定条款的 `provision_id`；`gold` 不因问题使用中文或英文而改变。

### 4.6 无对应条款

- 若问题在现行条款中确实无直接约束，不得强行标一条「最接近」的条款；该条应退回取证环节复核问题本身是否成立。
- 是否允许 `gold` 为空集、以及空集如何计入 Recall@5，PRD 未定义，列为待核实项（第 11 节），在确认前不得自行设定口径。

## 5. 正反例

> 以下条款号仅示意 `provision_id` 的格式，条款原文与编号以 `docs/条款树-v1.md` 为准；重点是判定思路，不是具体编号。

### 例 1：直接命中 vs 语义相邻

- **问题**：公司是否以书面形式记录用于建立并维持 GIPS 合规性的政策与程序？
- **正确标注**：`gold = ["1.A.5"]`，依据原文指向该条中「Document its policies and procedures」的义务句。
- **错误标注**：`gold = ["1.A.2"]`，理由写成「该条也提到 compliance，语义最接近」。
- **为什么错**：1.A.2 规定的是公司如何被定义（investment firm / subsidiary / division），与「书面记录政策与程序」没有直接义务关系。语义相似不等于直接约束；这正是「标注器选最像检索器想要的答案」的典型偏差。

### 例 2：多条款并列 vs 只标一条

- **问题**：GIPS 组合群报告是否必须列示至少五年的年度收益率，并披露组合群资产占公司总资产的比例？
- **正确标注**：`gold = ["4.A.1", "4.A.2"]`（前者约束至少五年的年度收益率，后者约束组合群资产占总资产比例的披露）。
- **错误标注**：`gold = ["4.A.1"]`，只标了与「收益率」字面最接近的一条。
- **为什么错**：问题含两项披露义务，漏标即 `gold` 不完整。抽检按「集合完全一致」判定，漏标计错，不按「命中一条即对」放宽。

### 例 3：条款级 vs chunk 级（粒度错误）

- **问题**：公司是否必须为所管理的各策略建立并维持组合群？
- **正确标注**：`gold = ["3.A.1"]`，指向「create composites for the firm's strategies」的义务句。
- **错误标注**：`gold = "chunk_7f3a…"`，或标成「该条款所在表格的某个单元格」。
- **为什么错**：评测对象是条款，不是 chunk。chunk_id 依赖某一次切分配置，换切分即失效，等于让 golden 绑定实现细节。

### 例 4：低置信项必须人工判定

- **问题**：公司采用 significant cash flow 政策时，是否必须在组合群报告中披露？
- **正确标注**：AI 给出 `gold = ["4.C.35"]`、`labeler_confidence` 偏低；人工抽检确认后写 `human_checked=true`，保留该 `gold`。
- **错误标注**：因置信度低而将 `gold` 留空，或直接把该条从评测集删除。
- **为什么错**：低置信只说明标注器不确定，不说明没有正确答案。留空会使该条无法参与 Recall@5 判定，抽检覆盖也随之失真；低置信项按规定必须全部被抽到。

### 例 5：条款版本错误

- **问题**：组合群定义发生变化时，是否允许追溯调整历史业绩？
- **正确标注**：`gold = ["3.A.6"]`（「Any change to a composite definition must not be applied retroactively」），且记录对应 `version_no` 为 GIPS 2020 现行版。
- **错误标注**：标到 3.A.1（建立组合群），理由是「同属 composite 相关条款」。
- **为什么错**：条款号接近不等于义务相同。gold 必须绑定现行版本、生效期与具体义务，否则评测的是另一条义务，指标失真。

## 6. 抽检规则

### 6.1 抽样量与覆盖

| 项 | 规则 |
|---|---|
| 比例 | ≥ 20% |
| 绝对量 | ≥ 40 条 |
| 场景覆盖 | 覆盖全部 5 类场景（A–E） |
| 语言覆盖 | 中英双语均须抽到（本规范约定，保证两种语言的 gold 都被核到） |
| 边界项 | **全部低置信项 + 全部表格类条款**必须入选，不参与随机 |
| 补齐方式 | 边界项之外随机补齐至 20%；若边界项本身已超过 20%，按边界项全量抽检（本规范约定） |

评测集 v1 为 200 条，20% 即 40 条，与「不少于 40 条」一致，因此最小抽检量为 40 条。

### 6.2 审查员判定口径

- 审查员独立判断 AI 给出的 `gold` 是否为该问题的正确条款集合。
- 判定结果只有「正确 / 错误」两种；**多标、漏标、错标、版本错误任一出现即计为错误**。
- 审查员不看检索结果、不看模型指标，裁决前不看其他审查员的结论。

### 6.3 adjudication 规则（分歧裁决）

> 以下为本规范约定的裁决规则。PRD 未展开裁决细节，但 M0 进入条件要求标注规范「含正例、反例与 adjudication 规则」，故在此定死口径。

- 审查员判定与 AI 初标不一致时：该条按「错误」计入抽检准确率，并写入 `error_reason`。
- 双人抽检时若两位审查员结论不一致：由第二位资深审查员裁决，以裁决结果为最终 `human_label`。
- 裁决后仍无法达成一致的条目：按「错误」计入（保守口径），并列入错误项清单，不得从分母中剔除。

### 6.4 抽检不通过的处理

- 抽检准确率 < 0.95：整批退回重标，不得冻结。
- 抽检必须覆盖的边界项若有遗漏：即使准确率达标，抽检本身判为不合格，须补抽后重算。

## 7. 自一致率的计算方式

### 7.1 定义

对第 `i` 条问题，固定 temperature 独立标注 3 次，得到三个 `gold` 候选集合。若至少两次结果完全相同（集合相等，与元素顺序无关），记 `self_consistency_i = 1`；否则记 `self_consistency_i = 0`。

3 次标注不存在「平票」，只存在两种情形：有至少两次相同（一致），或三次两两不同（不一致）。

### 7.2 公式

```
自一致率 SC = Σ(self_consistency_i) / N_valid

其中：
  N_valid = 完成全部 3 次有效标注的条目数（调用失败须重跑，不进入分母）
  self_consistency_i ∈ {0, 1}
```

判定：**SC ≥ 0.90 通过**；SC < 0.90 整批退回，先修标注器。

### 7.3 示例

**示例 A（通过）**

- 评测集 200 条，全部完成 3 次标注，`N_valid = 200`
- 181 条至少两次一致，19 条三次两两不同
- `SC = 181 / 200 = 0.905`
- 0.905 ≥ 0.90，自一致闸门通过

**示例 B（刚好压线）**

- `SC = 180 / 200 = 0.900`
- 阈值是「≥ 0.90」，压线通过；但该批次应重点看分歧项清单

**示例 C（不通过）**

- 177 条一致，23 条不一致
- `SC = 177 / 200 = 0.885`
- 0.885 < 0.90，整批退回，先修标注器再重标

### 7.4 与 gold 的关系

- 自一致率衡量**标注器稳不稳定**，不衡量**对不对**。
- 自一致率高但抽检准确率低，说明标注器稳定地错，仍按抽检闸门退回。
- `self_consistency` 同时写入条目级字段，供分歧项清单与低置信判定使用。

## 8. 抽检准确率的计算方式

### 8.1 定义

在抽检样本内，逐条比较人工判定与 AI `gold`：人工认为该 `gold` 正确记 1，否则记 0。正确条数除以抽检条数即为抽检准确率。

### 8.2 公式

```
抽检准确率 A = C / n

其中：
  n = 实际完成人工判定的抽检条数（分母，不得剔除错误项）
  C = 判定为「正确」的条数
```

判定：**A ≥ 0.95 通过**；A < 0.95 整批退回重标。

覆盖率同时须满足：`n / N ≥ 20%` 且 `n ≥ 40`（N 为评测集条目数）。

### 8.3 示例

**示例 A（通过）**

- 评测集 200 条，抽检 40 条（20%，满足 ≥ 40）
- 38 条判定正确，2 条错误
- `A = 38 / 40 = 0.950`
- 0.950 ≥ 0.95，抽检闸门通过

**示例 B（不通过）**

- 抽检 40 条，37 条正确，3 条错误
- `A = 37 / 40 = 0.925`
- 0.925 < 0.95，整批退回重标

**示例 C（扩大抽检仍不通过）**

- 因边界项较多，实际抽检 60 条（30%）
- 56 条正确，4 条错误
- `A = 56 / 60 ≈ 0.933`
- 0.933 < 0.95，整批退回；抽检比例更高不能抵消准确率不达标

### 8.4 与自一致率的区别

| 量 | 回答的问题 | 阈值 | 不通过的动作 |
|---|---|---|---|
| 自一致率 | 标注器稳不稳定 | ≥ 0.90 | 修标注器后整批重标 |
| 抽检准确率 | 标注器对不对 | ≥ 0.95 | 整批退回重标 |

两者任一不达标即阻断，不能互相替代（PRD 1.3、4.11.1）。

## 9. 为什么不用 Cohen's kappa

PRD 1.3 与 4.11 已明确弃用 kappa，理由照录并展开如下：

1. **kappa 度量的是两个标注者之间的一致性。** 本项目的流程是「AI 初标 + 人工抽检」，不是「两个人各标一遍」，不存在两个地位对等的标注者，算出的 kappa 在统计上没有意义。
2. **抽检不是全量双标。** 人工只判定抽检子集（≥ 20% 且 ≥ 40 条），与 AI 全量标注不构成可配对的双标注矩阵，kappa 的前提不成立。
3. **两个替代量更有判别力。** 自一致率衡量标注器稳不稳定，抽检准确率衡量标注器对不对；一个管「可重复」，一个管「正确」，正好对应 AI 初标的两类风险。
4. **两者任一不达标即阻断**，比单一一致性系数更直接地服务于发布判据（AC-24A、AC-24B）。

因此本规范**不计算、不报告 kappa**；评测报告中出现 kappa 视为口径错误。

## 10. 报告与冻结

### 10.1 双口径报告

评测报告必须同时给出两个 Recall@5：

| 口径 | 数据范围 | 用途 |
|---|---|---|
| AI 标注全量口径 | 全部 200 条 | 反映整体水平 |
| 人工抽检子集口径 | 抽检的 ≥ 40 条 | 反映 gold 可信度 |

- 两值差 **> 0.03** 时报告不合格，先查 gold 再谈模型（AC-24D）。
- 只报高值等于伪造指标（PRD 4.11.3）。
- 示例：全量 0.94、抽检子集 0.91，差 0.03，不触发「> 0.03」，报告可接受；若为 0.94 与 0.90，差 0.04，报告不合格。

### 10.2 结果落库

- 每次评测写 `eval_results`，`value` 用定点数字符串；缺 `config_hash` 的结果不得作为发布依据。
- 发布判据只能引用 `frozen_at` 非空的 `eval_sets` 版本。
- 评测集缺 `labeler_model` / `labeler_prompt_hash` 时，发布判据必须拒绝并提示补齐标注元数据（AC-24）。
- 接触过 golden 的 `model_snapshot_id` 不得再作为验收对象（AC-24C）。

### 10.3 冻结与变更

- 冻结后 `gold`、`content_hash`、`frozen_at` 三者绑定；任何改动走变更单并重新冻结。
- 更换标注器（`labeler_model` 或 `labeler_prompt_hash` 变化）视同换评测集版本，历史数字不可直接比较。
