# GIPS RAG 运维手册

适用版本：`0.1.0-M2`（`GET /healthz` 返回 `version`）
最后更新：2026-11-10（M5 交付演练）

本手册只写**已经在本仓库实现、能跑通**的操作。凡是没有对应接口或脚本的，明确写「本期无」，不给看起来能用的命令。

---

## 1. 部署

### 1.1 依赖与目录

| 项 | 位置 / 命令 |
|---|---|
| Python | 仓库虚拟环境中的 `python`（已加入 PATH） |
| 基础设施 | `docker compose up -d`（Milvus 2.4.6 + etcd + SeaweedFS S3 + Redis，卷为命名卷） |
| 模型权重 | `models/`（不入库）：`embed/`（bge-m3）、`rerank/`（bge-reranker-v2-m3）、`generate/qwen3-8b-q4_k_m.gguf` |
| 数据库 | `var/gips.db`（SQLite，WAL） |
| 原件与页文本 | `var/objects/`（本地对象存储，按 sha256 分两层目录） |
| 密钥与开关 | `.env`（不入库） |
| 运行产物 | `var/reports/`、`var/logs_backend.out/.err`（不入库） |

### 1.2 启动顺序

```powershell
# 1) 基础设施（等 milvus 健康检查通过，首次约 90 s）
docker compose up -d
docker compose ps

# 2) 后端（前台调试）
$env:GIPS_LLM_BACKEND = "fake"      # 生成走桩；真跑改为 llama_cpp
python -m uvicorn app.main:app --host 127.0.0.1 --port 8011

# 3) 前端操作台（静态页）
python -m http.server 8765 --bind 127.0.0.1 --directory frontend
```

- 后端启动即完成：配置校验 → SQLite 建表/触发器 → 回收崩溃遗留的中间态索引 → 组装显存池。
  **模型是惰性加载**，启动不占显存；第一个检索请求会触发冷加载（本机实测约 28 s，
  受 `retrieval_warmup_timeout_s=120` 保护，不计入通道超时）。
- 浏览器打开 `http://127.0.0.1:8765/`。前端跨域由后端 `CORSMiddleware` 放行（仅单机联调口径）。

### 1.3 健康检查

```powershell
Invoke-RestMethod http://127.0.0.1:8011/healthz
# {"status":"ok","version":"0.1.0-M2","llm_backend":"fake","resident_models":["embed","rerank"]}
```

`resident_models` 是显存池当前常驻槽位，用于和 `nvidia-smi` 交叉验证（8 GB 卡上不应同时出现 `generate` 与 `embed/rerank`）。

## 2. 备份

### 2.1 备什么、为什么

| 数据 | 是否必须备份 | 理由 |
|---|---|---|
| `var/gips.db` | **必须** | 台账、版本、审计、`cot_chains`、`egress_logs` 都在这里，丢了不可重建 |
| `var/objects/` | **必须** | 原件与页文本；页文本是引用回验的比对源，丢了回验就不能做 |
| Milvus 向量 | 可选 | 可由原件确定性重建（AC-73 实测 6.4 分钟，`index_version` 不变） |
| 模型权重 | 可选 | 可重新下载，注意版本要固定（R-44） |

### 2.2 备份命令

```powershell
# SQLite 在线备份（WAL 模式下可用，不会阻塞写入）
New-Item -ItemType Directory -Force var\backup | Out-Null
python -c "import sqlite3; s=sqlite3.connect('var/gips.db'); d=sqlite3.connect('var/backup/gips-20261110.db'); s.backup(d); d.close(); s.close()"

# 对象存储（文件级拷贝即可；拷贝期间不要执行补录/重建）
Copy-Item var\objects var\backup\objects-20261110 -Recurse
```

**不要**直接 `copy var/gips.db`：WAL 未落盘时会拿到不一致的快照，必须用 `sqlite3.backup`。

### 2.3 恢复

```powershell
# 1) 停后端，确认 8011 无监听
#    Get-NetTCPConnection -LocalPort 8011 -State Listen

# 2) 回放备份
Copy-Item var\backup\gips-20261110.db var\gips.db -Force
Remove-Item var\gips.db-wal, var\gips.db-shm -ErrorAction SilentlyContinue
Copy-Item var\backup\objects-20261110\* var\objects\ -Recurse -Force

# 3) 向量库丢了就重建（见第 4 节）；没丢可跳过
python scripts\rebuild_index.py --probe
python scripts\rebuild_index.py --rebuild --out var\reports\rebuild_drill.json

# 4) 起服务，跑一遍自生成评测确认 Recall@5 与基线一致
python scripts\run_selfeval.py --out var\reports\selfeval_restore.json
```

验收口径：`Recall@5 = 1.0000`、`index_version` 与备份前一致、`SELECT COUNT(*) FROM chunks WHERE status='active'` = 793。

## 3. 回滚

### 3.1 代码回滚

```powershell
git log --oneline -5
git checkout <上一个可用提交> -- app/ scripts/
# 依赖若有变化：pip install -r requirements.txt
```

约束：`db/schema.sql` 的迁移是**只进不退**（`init_schema` 里全是幂等 `ALTER`/建表，没有 down 脚本）。
回滚代码前先备份 `var/gips.db`；新代码写入的新列在旧代码里只是不被读取，不会炸，但也不能靠旧代码回退数据。

### 3.2 索引 / 文档版本回滚

本期**没有**版本切换接口（`API-20 /documents/{id}/versions`、`API-21 /publish`、`API-22 DELETE`
在接口文档里有定义，但当前未实现）。只有两条可用路径：

1. **换回旧版本**（人工 SQL，需先备份）：

```sql
-- 以 gips2020 为例：把 2 版置为 superseded，1 版恢复 active
UPDATE chunks    SET status='superseded' WHERE doc_id='gips2020' AND version_no=2;
UPDATE chunks    SET status='active'     WHERE doc_id='gips2020' AND version_no=1;
UPDATE documents SET status='published', index_status='active', active_version=1
  WHERE doc_id='gips2020' AND version_no=1;
```

2. **用旧原件重新入库**：`POST /documents` 指定新的 `version_no`。
   注意同一 `doc_id` + 同一字节会被判为幂等上传并直接返回 `duplicate: true`（不会新建版本）,
   所以这条路径要求「旧原件内容与库里的某版本不同」，否则只能走路径 1。

回滚后必须重跑 `run_selfeval.py`，确认检索已切到目标版本。

### 3.3 配置回滚

`.env` 改错导致启动失败时，按 1.2 的启动顺序重启即可；配置校验失败会**拒绝启动**（这是设计，不是故障），
错误信息会指出具体键名。

## 4. 故障处置

### 4.1 速查表

| 现象 | 先看什么 | 处置 |
|---|---|---|
| 接口全 5xx，`healthz` 也不通 | 进程是否在；`var/logs_backend.err` | 重启后端；端口占用见 4.2 |
| 检索报错 / 召回为空 | `docker compose ps`；Milvus 19530 | 起 Milvus；集合丢了走 4.3 |
| 上传返回 504 `UPSTREAM_TIMEOUT` | `egress_logs` 最近一行 | 无文本层页面走云 OCR 失败 → 转人工复核；确认 `GIPS_EGRESS_ENABLED` 与供应商状态 |
| 上传返回 503 `GPU_UNAVAILABLE` | 日志 `gpu_oom` 事件里的 `resident` / `ctx_tokens` / `batch_size` | 见 4.4 |
| 问答很慢但不报错 | `GET /reviews/{task_id}` 的 `queue_position` | 排队正常；持续高则降并发或扩机器（单机并发恒为 1） |
| 引用回验失败增多 | 日志 `qa_citation_unverified` | 索引与原件不一致，按 4.3 重建并比对 `index_version` |

### 4.2 端口占用

```powershell
Get-NetTCPConnection -LocalPort 8011 -State Listen |
  ForEach-Object { Get-CimInstance Win32_Process -Filter "ProcessId=$($_.OwningProcess)" }
Stop-Process -Id <PID> -Force
```

### 4.3 Milvus 数据丢失 / 索引不可用

1. 确认：`python scripts/rebuild_index.py --probe` → `collection_exists=false`
2. 重建：`python scripts/rebuild_index.py --rebuild --out var/reports/rebuild_drill.json`
3. 重启后端（旧客户端句柄指向已被删除的集合）
4. 复测：`python scripts/run_selfeval.py`，Recall@5 应为 1.0000

实测 RTO ≈ 6.9 分钟（重建 6.4 分钟 + 重启 3.2 s + 首次查询冷加载约 28 s），详见 `reports/恢复演练.md`。
**注意**：系统不会自动发现向量库丢失——`documents.index_status` 仍是 `active`。发现手段目前只有
「检索结果异常」和人工对账，这是已记录缺口（OBS-M5-01）。

### 4.4 显存不足（OOM）

`GPUPool` 在 OOM 时会把现场写入 `oom_snapshots` 并打 `gpu_oom` 日志，然后返回 503 `GPU_UNAVAILABLE`。
处置顺序：

1. 看日志里的 `resident`：8 GB 卡上 `generate` 与 `embed`/`rerank` **不允许同时常驻**（硬禁令 2）。
2. 确认生成侧 `ctx_tokens ≤ 4096`、并发 1（R-46）。
3. 不要手工「多留一点余量」去调大 batch；先降 `batch_size` 或上下文，再重启进程回收碎片。

### 4.5 关闭 / 打开云通道（降级开关）

```powershell
# 关闭：只读与检索照常，需要 OCR 的写请求会失败并标 ocr_failed
$env:GIPS_EGRESS_ENABLED = "false"
# 打开：恢复云 OCR
$env:GIPS_EGRESS_ENABLED = "true"
```

改动后需重启后端（配置在启动时读取）。实测降级耗时 3.23 s，见 `reports/压测报告.md` 第 4 节。
注意：**当前阿里云 OCR 返回 401 `ocrServiceNotOpen`、腾讯云凭据为占位符**，
打开开关也不代表扫描件能入库；有文本层的 PDF 不受影响。

### 4.6 停止服务

```powershell
# 后端：找到 8011 的 PID 后 Stop-Process；进程退出时会 pool.shutdown() 释放显存
docker compose down          # 保留数据卷；加 -v 会删数据卷，慎用
```

## 5. 日常巡检

| 频率 | 检查项 | 命令 / 位置 |
|---|---|---|
| 每次变更后 | 四道门禁 | `python v1-spec/tools/spec_sync.py --root v1-spec` 等，见项目规则 |
| 每日 | `healthz`、磁盘剩余、`var/logs_backend.err` 有无 `gpu_oom` | - |
| 每周 | 台账与向量库条数对账 | `SELECT COUNT(*) FROM chunks WHERE status='active'` vs `rebuild_index.py --probe` 的 `row_count_total` |
| 每周 | 备份完整性 | 用 `sqlite3.backup` 的副本 `PRAGMA integrity_check` |
| 每月 | 恢复演练抽一次 | 第 4.3 节流程，记录 RTO |

**监控缺口（照实记录）**：接口文档里的 `GET /metrics`（API-38）当前未实现，
显存、队列、通道时延只能从日志与 `reviews/{task_id}.queue_position` 间接看。
上线前若要接监控，需先补该接口或接日志采集。
